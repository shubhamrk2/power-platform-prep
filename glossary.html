PART 09

Glossary & Abbreviations

Every term from Power Platform, Dataverse, ALM, DLP, Flows, MCP, and AI integration — plain English with a general example and a real project example for each.

Power Platform — The Suite#

Microsoft's low-code / no-code ecosystem. Five pillars sharing one identity layer (Azure AD), one data layer (Dataverse), and one admin center (PPAC).

Suite
Power Platform

Five tools — Power Apps, Power Automate, Power BI, Power Pages, Copilot Studio — that share Dataverse as a common data layer, Azure AD for identity, and PPAC for admin governance. You can build an app, automate a workflow, and visualize data without leaving Microsoft's cloud.

📌 General: A team builds a leave-request form (Power Apps), auto-emails the manager (Power Automate), and tracks approvals in a dashboard (Power BI) — all connected to the same Dataverse table.

🔧 Project: The T-Mobile MCP server exposes all three layers — Apps, Automate, and Dataverse — via 111 tools, letting Claude Code read and manage the entire platform over SSO.

App building
Power Apps

The app-building pillar. Two models: Canvas App (you design every pixel; uses Power Fx) and Model-Driven App (UI auto-generated from Dataverse schema; best for structured data portals).

📌 General: A field-service app where technicians fill in inspection forms on a tablet with a custom logo and color scheme.

🔧 Project: MCP tools list_apps, get_app enumerate all Power Apps in an environment so Claude can report which apps exist without opening the maker portal.

Automation
Power Automate

The workflow automation pillar. Builds "when… do…" recipes called flows. Formerly Microsoft Flow. Three types: Cloud Flow (server-side, event or schedule), Desktop Flow (RPA, controls desktop UIs), Business Process Flow (guided multi-step process for users).

📌 General: When a SharePoint form is submitted, send an approval email, wait for response, then update a Dataverse row.

🔧 Project: MCP tools list_flows, run_flow, get_flow_run_history let Claude trigger and inspect flows without using the maker portal UI.

Analytics
Power BI

Business intelligence and data visualization. Connects to data sources, transforms data with Power Query (M language), builds a semantic model with DAX measures, and publishes interactive reports. Supports Row-Level Security (RLS) using USERPRINCIPALNAME().

📌 General: A monthly sales dashboard with slicers by region and a bar chart of revenue by product category.

🔧 Project: A library usage report showing top borrowed books and overdue rates — RLS ensures each member sees only their own loan history via USERPRINCIPALNAME() DAX filter.

AI Agents
Copilot Studio

No-code canvas for building AI chatbots and copilots. Formerly Power Virtual Agents. Can call flows, query Dataverse, invoke Azure OpenAI, and integrate with Teams. Topics define conversation paths; knowledge sources feed the AI for generative answers.

📌 General: An HR chatbot that answers leave-policy questions from a SharePoint document and escalates to a human agent when stuck.

🔧 Project: The JD cites Copilot Studio. Your stronger answer: the MCP server IS the tool layer that Copilot Studio agents run on — you built the plumbing, not just the surface.

Web portals
Power Pages

Build external-facing websites connected to Dataverse. Supports anonymous and authenticated access, configurable security, and Liquid templating. Replaces the old "Power Apps Portals" branding.

📌 General: A partner portal where external vendors submit support tickets that land directly in a Dataverse table without needing a Microsoft account.

Environments & Tenants#

The isolation boundary between DEV, UAT, and PRD — and between different organizations sharing Microsoft's cloud.

Identity
Tenant

An organization's dedicated, isolated space in Microsoft's cloud, identified by a domain (e.g. contoso.onmicrosoft.com). One Microsoft 365 contract = one tenant. All users, licenses, and environments for that org live inside it. Users in different tenants cannot see each other's environments by default.

📌 General: Accenture is one tenant; T-Mobile is a separate tenant — employees cannot see each other's Dataverse environments.

🔧 Project: Your E5 trial tenant is shubhamrk2.onmicrosoft.com. The MCP server authenticates against this tenant via browser SSO — the bearer token is tenant-scoped.

Container
Environment

An isolated container inside a tenant that holds apps, flows, Dataverse tables, and connections. Types: Default (everyone can access — avoid for production), Developer (personal, free, for building), Sandbox (resettable, for testing), Production (live users). URL pattern: orgname.crm8.dynamics.com.

📌 General: DEV environment for building, UAT for testing, PRD for 500 live users — each a separate container so a DEV mistake can never affect PRD.

🔧 Project: PP-DEV (ppdev258.crm8.dynamics.com), PP-UAT, PP-PRD — three Developer environments, the maximum per user on the Developer Plan. MCP tool list_environments enumerates all of them.

Admin
Admin Center (PPAC)

Power Platform Admin Center at admin.powerplatform.microsoft.com. Where Global Admins and Power Platform Admins manage: environments, DLP policies, user licenses, Dataverse capacity, analytics, and audit logs. The GUI equivalent of Get-AdminPowerAppEnvironment in PowerShell.

📌 General: An admin creates a new Sandbox environment, assigns 3 users as Environment Admins, and applies a DLP policy — all from PPAC.

🔧 Project: Day 1 of the 7-day plan — verify DLP authoring is available at PPAC → Policies → Data policies. Get-DlpPolicy returned {} confirming no tenant-level policies block you.

Build URL
Maker Portal

make.powerapps.com — where makers build canvas apps, model-driven apps, flows, and solutions. Always check the environment picker (top-right) before building — the wrong environment is the #1 cause of "missing" components.

📌 General: Switch environment dropdown from "Default" to "PP-DEV" before creating a new table, otherwise the table lands in the wrong environment.

ALM & Deployment#

Moving apps from DEV to UAT to PRD in a controlled, repeatable, auditable way.

Process
ALM — Application Lifecycle Management

The discipline of moving apps through controlled stages: DEV (build) → UAT (test) → PRD (live users). Prevents "cowboy fixes" directly in production. In Power Platform, ALM is implemented via Solutions (export/import) or Power Platform Pipelines (one-click automated). Pairs with source control via PAC CLI.

📌 General: A team builds a flow in DEV, tests it with UAT users for two weeks, then deploys the managed solution to PRD — changes are traceable and reversible.

🔧 Project: Day 3 of the 7-day plan is ALM + PAC CLI. You'll demo pac solution export --managed then import into TEST environment — a live walkthrough of the full pipeline.

Container
Solution

A zip-like deployment container that packages Power Platform components — apps, flows, tables, security roles, environment variables, connection references — for moving between environments. Every customization that needs to be promoted to UAT/PRD must be inside a solution.

📌 General: "HR Onboarding Solution v2.3" contains 2 canvas apps, 4 flows, 6 tables, 1 model-driven app, 3 environment variables.

🔧 Project: MCP tool list_solutions returns all solutions in the current environment; export_solution triggers an async export job and downloads the zip.

Deployment
Managed Solution

A solution exported in locked/read-only mode. Once imported to UAT or PRD, nobody — not even the creator — can edit apps or flows directly in that environment. All changes must go through DEV → export → re-import. Enforces ALM discipline and protects live environments.

📌 General: You import a managed payroll app to production — the CFO can run it but nobody can accidentally modify the approval logic at 5pm on a Friday.

Dev only
Unmanaged Solution

The editable version of a solution, kept in the DEV environment. All components are fully customizable. When you export, you choose: Managed (for UAT/PRD) or Unmanaged (for backup or to share with another developer). The DEV environment always holds the unmanaged solution — it's the source of truth.

📌 General: A developer opens the unmanaged solution in DEV, edits a flow, then exports it as Managed and imports to UAT — the UAT version is locked, the DEV version remains editable.

Namespace
Publisher

An identifier for the creator of a solution, prepended as a prefix to all custom table and column schema names. Prevents naming collisions when multiple solutions coexist in the same environment. Format: prefix_columnname. Default Dataverse publisher uses prefix cr.

📌 General: Publisher "Contoso HR" with prefix chr → all custom columns are chr_employee_id, chr_department — distinguishable from other solutions' columns.

🔧 Project: When querying Dataverse via OData in the MCP server, custom table/column names always include the publisher prefix. Knowing this avoids the common mistake of using display names instead of schema names in filter queries.

Config per env
Environment Variable

A named value stored in a solution that holds different values per environment without changing any code. Types: String, Number, Boolean, JSON, Data Source. Flows and apps read the variable by name — you set the value during solution import into each environment. Essential for clean ALM.

📌 General: ApiEndpoint = https://dev-api.company.com in DEV; https://api.company.com in PRD. The same flow works in both environments; only the variable value differs.

🔧 Project: A library system uses LoanPeriodDays = 14 in DEV (generous for testing) and 7 in PRD. The canvas app reads this via LookUp() instead of hard-coding 14 — no code change needed when promoting.

ALM
Connection Reference

A solution-level named pointer to a connection (an authenticated connector instance). Instead of hard-coding "which Outlook account sends emails," the solution stores a connection reference. When you deploy to UAT, an admin reconnects it with UAT credentials during the import wizard — zero code changes. The connection itself is NOT inside the solution; only the reference is.

📌 General: "NotifyViaOutlook" connection reference → dev@company.com in DEV, prod-notify@company.com in PRD — same solution, different connections.

🔧 Project: Any solution with Outlook or Dataverse flows needs connection references — demonstrating this during the interview is a strong signal you understand real ALM, not just theory.

Automation
Pipeline (Power Platform Pipelines)

A free, built-in tool that automates DEV→UAT→PRD deployment with a single "Deploy" button. Replaces the manual export→download→upload cycle. Configured in the admin center. On deployment, prompts to reconnect connection references and set environment variable values per target environment.

📌 General: Set up a pipeline with DEV as source, UAT as first stage, PRD as second stage. A maker clicks "Deploy to UAT" and the pipeline handles export + import + validation.

🔧 Project: Day 3 of the 7-day plan — demo Pipelines as the "one-click ALM" story for the interview, contrasted with the PAC CLI approach for advanced scenarios.

CLI
PAC CLI

Power Apps CLI (pac command) — a cross-platform command-line tool for Power Platform. Installed via .NET SDK. Key commands: pac auth create, pac env list, pac solution export --managed, pac solution import, pac canvas pack/unpack (for source control). The scriptable alternative to the maker portal UI.

📌 General: pac solution export --path ./myapp.zip --managed exports a managed solution to a local zip, ready to commit to Git or import elsewhere.

🔧 Project: Day 3 of the 7-day plan. pac auth create --url https://ppdev258.crm8.dynamics.com authenticates against PP-DEV; pac solution list shows all solutions in that environment.

Dataverse#

Microsoft's managed cloud-relational database built for Power Platform. Formerly Common Data Service (CDS). The backbone of all serious Power Platform solutions.

Database
Dataverse

Microsoft's managed, cloud-hosted relational database built specifically for Power Platform. Provides built-in security roles, row-level security, audit logging, field-level security, business rules, relationships, and a REST API (OData). URL hint: crm8 in your environment URL = CRM/Dataverse backend, region 8 = India/APAC. Formerly Common Data Service (CDS).

📌 General: Store customer records in Dataverse instead of Excel — it scales to millions of rows, has built-in role-based access control, and connects natively to Power Apps and Automate.

🔧 Project: The MCP server's Dataverse tools call the OData API (/api/data/v9.2/) with SSO bearer tokens. list_tables → GET /EntityDefinitions. get_rows → GET /tablename?$filter=... create_row → POST /tablename (write-mode only).

Schema
Table

Dataverse equivalent of a database table (formerly "Entity"). Contains columns (fields) and rows (records). Has a Display Name (human-readable, e.g. "Loan") and a Schema Name (code name with publisher prefix, e.g. cl_loan). System tables like Account and Contact come pre-built; custom tables are prefixed.

📌 General: An Order table holds OrderDate, CustomerName, TotalAmount — one row per order placed.

🔧 Project: MCP list_tables returns both system and custom tables. In the library system, cl_book, cl_member, cl_loan are custom tables with the cl publisher prefix.

Schema
Column (Field)

A field/attribute in a Dataverse table (formerly "Attribute"). Has a data type: Text, Number, Date/Time, Choice, Lookup, Boolean (Yes/No), Currency, Image, File, Multiline Text, Calculated, Rollup. Choice and Lookup are the two most important to understand for relationships and validation.

📌 General: An Email column — data type: Email (validates format), required, max 200 chars.

🔧 Project: MCP get_table_metadata returns column definitions including schema names — critical because OData filters must use schema names, not display names.

Data
Row (Record)

One record in a Dataverse table. Has a unique GUID as its primary key (the tablename + id column, e.g. cl_loanid). All operations on a specific record require its GUID. Rows have an owner (a user or team) which drives row-level security.

📌 General: One customer record in the Customers table — GUID: 3f4a5b6c-1234-5678-abcd-ef9012345678.

🔧 Project: MCP get_row(table, row_id) fetches one specific Dataverse row by its GUID. update_row and delete_row also require the GUID — you cannot update by name, only by ID.

Identity
GUID

Globally Unique Identifier — a 36-character alphanumeric string that uniquely identifies every row in Dataverse and most Microsoft systems. Format: xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx. Generated automatically. Cannot be changed after row creation. The ?$select=columnname&$filter=id eq guid'...' pattern in OData always uses GUIDs.

📌 General: Every Dataverse row, every Azure resource, every M365 user has a GUID. When you see a long hex string in a URL or API response, that's a GUID.

🔧 Project: MCP run_flow takes the flow's GUID, not its display name. _resolve_args in the server translates human-readable names ("Daily Overdue Reminder") to GUIDs before calling the API — that name-resolution logic was a key design decision.

Schema
Relationship (1:N / N:N)

A link between two Dataverse tables that maintains referential integrity. Most common: One-to-Many (1:N) — created by adding a Lookup column on the "many" side. Many-to-Many (N:N) — uses an intersection table. Relationships enable navigation in OData: $expand=cl_book($select=cl_title) fetches the related book's title in one query.

📌 General: Customer (1) → Orders (N) — the Orders table has a CustomerID lookup column pointing to the Customers table.

🔧 Project: The library system: Books 1:N Loans, Members 1:N Loans. In MCP OData queries, $expand avoids N+1 queries — fetch all loans and their book titles in one API call instead of one call per loan.

Column type
Lookup Column

A column that stores the GUID of a row in another table, creating a relationship. Rendered as a dropdown showing the primary name column of the target table. In OData responses, lookups appear as _fieldname_value (the GUID) and _fieldname_value@OData.Community.Display.V1.FormattedValue (the display name).

📌 General: ManagerID lookup on an Employee table → points to another Employee row (the manager). Power Apps renders this as a searchable dropdown of all employees.

🔧 Project: MCP OData filter on Loans: _cl_member_value eq guid'...' — the lookup column is referenced with the _value suffix in OData, not the column's display name.

Column type
Choice Column (Option Set)

A column with a fixed set of selectable values (like a dropdown). Values are stored internally as integers, displayed as labels. Two types: Local (defined on this column only) and Global (shared across multiple columns/tables). Formerly called "Option Set." In OData, filter by integer value: statuscode eq 1.

📌 General: Priority column: Low(1), Medium(2), High(3), Critical(4) — stored as 1-4 in the DB, shown as text labels in the UI.

🔧 Project: cr_membership_type Choice column with values Premium, Standard, Senior, Student. OData filter: cr_membership_type eq 879840000 (the integer code for "Premium").

Query
OData Filter

The query language for filtering Dataverse rows via REST API. Appended to the URL as ?$filter=expression. Operators: eq, ne, lt, gt, le, ge, and, or. Functions: contains(), startswith(), endswith(). Also supports $select (columns), $expand (related tables), $orderby, $top.

📌 General: GET /cl_loans?$filter=cr_returned eq false and cr_due_date lt 2025-01-01&$select=cr_loan_date,cr_due_date&$expand=_cl_member_value($select=cr_email)

🔧 Project: MCP get_rows takes an OData filter string as input. Users type natural language; the server (or Claude) translates it to OData. E.g. "all overdue loans" → cr_returned eq false and cr_due_date lt @{utcNow()}.

No-code logic
Business Rule

Logic applied directly on a Dataverse table or form — no code, no flow. Fires when a record opens or a field changes. Can: show/hide fields, set field values, validate, lock/unlock fields, display error messages. Runs on the server (always) and client (when supported). Cannot access related tables or run async operations.

📌 General: If Contract Type = Fixed Price, make the Budget field required and lock the Hourly Rate field — no code, configured as a rule in the table designer.

Canvas Apps & Power Fx#

The pixel-control app model and its Excel-like formula language. Different from Power Automate expressions — same platform, completely different syntax.

App type
Canvas App

An app where you design every pixel of the UI — drag controls onto screens, set properties with Power Fx formulas. Best for mobile apps, custom UX, or when the UI must match a specific design. Connects to Dataverse, SharePoint, SQL, REST APIs, or any connector. Runs in a browser or the Power Apps mobile app.

📌 General: A field technician app with a custom logo, barcode scanner input, and a gallery showing nearby work orders — exact pixel placement, company colors, custom navigation.

App type
Model-Driven App

UI auto-generated from your Dataverse schema — you configure views, forms, and sitemap rather than designing pixels. Best for data-heavy admin portals and structured workflow apps. Includes built-in search, related records, business process flows, dashboards. Always requires Dataverse.

📌 General: A customer service portal for agents — standard form layouts, sidebar navigation, drill-down into related cases — configuration-driven, no design time needed.

Power Fx
Power Fx

The Excel-like formula language of canvas apps. Declarative: you describe WHAT the result should be, not HOW to compute it. No semicolons between arguments (uses commas). Dot notation for control properties: GalleryName.Selected.cr_title. Everything re-evaluates automatically when inputs change — like a spreadsheet cell.

📌 General: If(IsBlank(EmailInput.Text), "Required", EmailInput.Text) — if the text box is empty, show "Required"; otherwise show the typed value.

🔧 Key formulas: Filter(table, condition) · Search(table, text, column) · LookUp(table, condition) · Patch(table, record, changes) · Remove(table, record) · Navigate(screen) · Notify(msg, type) · CountRows(table) · DateAdd(date, n, Days) · User().Email

Control
Gallery

A canvas app control that repeats a template for every row in a data source — like a list view. The Items property is a Power Fx expression (usually Filter() or Search()). Gallery.Selected holds the currently tapped item. Supports vertical, horizontal, and flexible-height layouts.

📌 General: A gallery connected to Filter(SupportTickets, Status = "Open") — shows one card per open ticket, updating live as tickets are closed.

Control
Form (EditForm / DisplayForm)

Canvas app controls for viewing (DisplayForm) or editing (EditForm) one Dataverse row at a time. Key functions: SubmitForm(BookForm) saves changes; NewForm(BookForm) clears for a new record; EditForm(BookForm) switches to edit mode; ResetForm(BookForm) discards changes. BookForm.Valid is true only when all required fields are filled.

📌 General: An EditForm connected to the Employees table lets an HR manager update salary and department — SubmitForm button saves to Dataverse instantly.

Security
Row-Level Security in Canvas Apps

Filter gallery Items using User().Email — the currently signed-in user's UPN — so each person sees only their own rows. This is a client-side filter and should always be backed by Dataverse security role access levels (User scope) to enforce it server-side too.

📌 General: Filter(Loans, 'cr_member (Members)'.cr_email = User().Email && cr_returned = false) — each member sees only their own active loans, regardless of what's in the table.

Power Automate & Flows#

The when/do automation engine. Cloud flows run server-side; expressions inside flows use Azure Logic Apps syntax — NOT Power Fx.

Workflow
Flow

An automated workflow in Power Automate. Has exactly one trigger and one or more actions. Three types: Cloud Flow (runs in Microsoft's cloud — most common), Desktop Flow (RPA — controls desktop UIs via UI automation), Business Process Flow (guided multi-step process shown to users on a model-driven form).

📌 General: "When a new row is added to the Leads table, send a welcome email and create a follow-up task" — a Cloud Flow with an automated trigger.

🔧 Project: MCP tools list_flows, get_flow, run_flow, get_flow_run_history — you can trigger any instant flow and poll its run history entirely through the MCP server without touching the maker portal.

Trigger
Trigger Types

What starts a flow. Every flow has exactly one. Automated: fires when an event happens (Dataverse row added/modified, email received, Teams message). Scheduled: fires at a set time (daily at 9 AM, every 15 minutes). Instant: fires when a human clicks a button (in a flow app, Teams, or Power Apps button). PowerApps: a special instant trigger called by a canvas app — enables passing parameters to the flow and receiving outputs back.

📌 General: Scheduled trigger → "every day at 9 AM, check for overdue loans and email each member." Instant trigger → "Return Book" button in an app calls the flow with a loan ID.

Step
Action

One step inside a flow that does something. Examples: Get a row (Dataverse), Send an email (Outlook), Post a message (Teams), HTTP (raw API call), Condition (if-else), Apply to each (loop), Scope (group/try-catch), Initialize variable, Set variable, Compose, Delay. Each action produces output (accessible via dynamic content or expressions in subsequent steps).

📌 General: Action 1: "Get a row" from Dataverse (loan record). Action 2: "Send an email" to the member's email address retrieved from Action 1's output.

Logic
Condition & Apply to Each

Condition: if-else branch — evaluates a true/false expression, runs different actions on each branch. Can be nested. Apply to each: a loop — runs a sequence of actions for every item in an array (usually from a "List rows" Dataverse action). Equivalent to forEach in code. Heavy loops can hit flow run time limits (30 days max; 5000 actions per run default).

📌 General: "List rows" returns 15 overdue loan records. "Apply to each" loops over them: Condition checks if days overdue > 30 → Yes branch sends escalation email; No branch sends standard reminder.

Formula
Expression (Flow)

Formula language used inside Power Automate action fields. Based on Azure Logic Apps expression language — different from Power Fx. Written in the expression tab of the dynamic content picker. Wrapped in @{...} when embedded in strings. Key functions: utcNow(), addDays(), formatDateTime(), items('loop_name')?['column'], outputs('action_name')?['body/field'], if(), mul(), div(), ticks().

📌 General: addDays(triggerBody()?['cr_loan_date'], 14) — calculates due date 14 days after loan date. formatDateTime(utcNow(), 'dd MMM yyyy') — today's date formatted for email body.

Reusable
Child Flow

A flow designed to be called BY another flow (the parent). Must use "Manually trigger a flow" as its trigger with defined input parameters. Must be in the same solution as the parent. Executes its logic, then returns output values via "Respond to a PowerApp or flow" action. Cannot call itself (no recursion). Cannot be triggered directly by a user.

📌 General: "Calculate Tax" child flow — receives Amount (number), applies tax logic, returns TaxAmount (number). Any sales flow that needs tax calls this one flow instead of duplicating the logic.

🔧 Interview answer for "how do you create a parent flow calling a child flow?": (1) Build child with Manually trigger a flow trigger + input params. (2) End child with Respond to a PowerApp or flow + output params. (3) Both must be in the same solution. (4) In parent, add action "Run a child flow" (Flow connector), select child, map inputs, read outputs from dynamic content.

Caller
Parent Flow

A flow that calls one or more child flows using the "Run a child flow" action (found under the Flow connector in Power Automate). Passes inputs to the child and reads the child's returned outputs via dynamic content. Key constraint: parent and child must be in the same solution and same environment. Parent can call multiple children sequentially or (with parallel branches) concurrently.

📌 General: "Process Book Return (Parent)" → calls "Calculate Late Fee (Child)" → calls "Send Return Confirmation (Child)" → updates the loan row in Dataverse. The parent orchestrates; the children execute reusable logic.

Output
Respond to a PowerApp or flow

The action that returns output values from a child flow (or from any flow triggered by PowerApps) back to the caller. Must be the last action in the flow. Without this action, the parent flow cannot read any result from the child — it just calls it and moves on blind. Each output is named and typed (Text, Number, Boolean, Object).

📌 General: Child flow "Get Manager Name" ends with this action, returning manager_name (Text) and manager_email (Text). Parent reads both from dynamic content after the "Run a child flow" step.

Error handling
Scope

A container action that groups other actions. Primary use: error handling (try/catch pattern). Set the "catch" scope's "Configure run after" to "has failed" — it runs only when the try scope fails. The catch scope can send an alert email, log to Dataverse, or retry. Without Scopes, a failing action stops the entire flow.

📌 General: Scope "Try" → create row, send email. Scope "Catch" (runs if Try fails) → send alert to admin@company.com with the error message from result('Try_scope')?[0]['error']['message'].

Utility
Compose

A simple action that calculates and stores a single value — like a named variable but for any expression. Useful when the same expression is needed in multiple later steps (avoids repeating the expression). Output accessed as outputs('Compose_action_name').

📌 General: Compose "TodayFormatted" = formatDateTime(utcNow(), 'yyyy-MM-dd'). Three later steps reference outputs('TodayFormatted') instead of repeating the expression — one change updates all three.

Connectors & Connections#

The bridges between Power Platform and external services. Standard = free. Premium = requires per-user license or Developer Plan.

Bridge
Connector

A pre-built API wrapper that connects Power Platform to an external service. Hides raw HTTP behind a friendly action/trigger interface. Standard (free with M365/Power Platform): SharePoint, Outlook, Teams, OneDrive, Excel Online, Office 365 Users, Approvals, Notifications, Microsoft Lists. Premium (requires Developer Plan or per-user license): Dataverse (direct), HTTP, SQL Server, SAP, Salesforce, Azure services, Custom connectors.

📌 General: The SharePoint connector lets you "Get items from a list" without knowing the SharePoint REST API — authentication, URL construction, pagination all handled for you.

🔧 Project: The MCP server is effectively the Python equivalent of a premium custom connector — it wraps Power Platform REST APIs with authentication, error handling, and a typed interface. But it runs outside Power Platform, so no DLP policy applies.

Auth
Connection

One authenticated instance of a connector — the specific "who" behind a connector. Created when a maker signs in to a service while adding a connector action. Connections are per-user and per-environment. They are NOT stored in solutions (connection references are). A flow's connections are visible under Power Automate → My connections.

📌 General: Outlook connector connected as admin@company.com = one connection. Same connector connected as notifications@company.com = a different connection. Two people running the same flow use their own connections for their own actions.

ALM
Connection Reference

A solution-level named pointer to a connection. Stored inside the solution; the actual connection it points to is set per-environment during deployment. When you import a solution to UAT, the wizard prompts you to link each connection reference to an existing connection in that environment — no flow code changes needed.

📌 General: "OutlookNotifyRef" connection reference in the solution → linked to dev@co.com in DEV, prod-alerts@co.com in PRD. Same flow YAML, different senders per environment.

Premium
HTTP Connector

Allows a flow to make raw REST API calls to any URL with custom headers, body, and auth (Basic, API Key, OAuth). The most flexible connector — if a service has an API, HTTP can reach it. Requires Premium license. Subject to DLP policies — admins can block it or restrict it to specific environments.

📌 General: Call a weather API, pass city name as query param, get temperature JSON back — no dedicated weather connector needed.

🔧 Project: The MCP server is the Python equivalent of the HTTP connector — it calls Power Platform REST APIs with bearer tokens. The advantage: it runs outside Power Platform entirely, so no connector license, no DLP restriction.

Custom
Custom Connector

A user-defined connector built from an OpenAPI (Swagger) spec or built manually. Appears alongside built-in connectors in the maker portal. Can define authentication (API key, OAuth), actions (GET/POST/PATCH endpoints), and triggers (webhook-based). Requires Premium for use in production.

📌 General: An internal HR API (api.hr.company.com) wrapped as a custom connector — makers can now add "Get Employee by ID" as a flow action without knowing the API URL or auth mechanism.

🔧 Project: If you wanted to expose MCP server functionality back into Power Automate, a custom connector wrapping the server's HTTP API would be the approach. This would be an interesting interview talking point.

Push
Webhook

An HTTP callback — your server registers a URL; when an event occurs, the event source POSTs data to that URL. Used in automated flow triggers where services push events rather than being polled. Power Automate manages webhook registration/deregistration automatically for supported connectors.

📌 General: A payment gateway POSTs to your flow's webhook URL when a payment completes — your flow processes the result without polling the gateway every minute.

🔧 Project: The MCP server uses stdio transport (not HTTP webhooks) for Claude-to-server communication — but the conceptual model is similar: an event arrives, the receiver processes it asynchronously.

Security & Governance#

Two layers: (1) Dataverse security roles control who can read/write which rows. (2) DLP policies control which connectors can combine in flows. Both are essential for enterprise governance stories.

Permissions
Security Role

A permission set in Dataverse defining what a user can Create, Read, Write, Delete, Append, Append To, Assign, and Share on each table, at a specific scope. Assigned to users directly or via teams. Two levels always assigned: Environment role (System Admin or Basic User — set in Admin Center) and Dataverse security role (custom roles you create in the environment settings).

📌 General: "Sales Manager" role: full CRUD on Opportunities org-wide, Read-only on Accounts org-wide, no access to HR tables at all.

🔧 Project: MCP server operates under the authenticated user's security role — if that user is Basic User with Read-only on Flows, the MCP run_flow tool will fail with a 403. This is the "secure by default" design: users only ever see what their own permissions allow.

Permissions
Access Level (Privilege Scope)

The scope at which a privilege applies within a security role. Four levels: User (rows you own only), Business Unit (rows owned by members of your BU), Parent: Child Business Units (BU + child BUs), Organization (all rows regardless of owner). This is what drives row-level security in Dataverse without any code.

📌 General: A salesperson has "Read" at User level on Opportunities → sees only their own opportunities. A sales director has "Read" at Organization level → sees all 10,000 opportunities company-wide.

RLS
Row-Level Security (RLS)

Ensuring each user sees only data they're authorized to see. Three implementations: (1) Dataverse: security role access levels + row ownership. (2) Canvas App: Filter(table, column = User().Email) client-side. (3) Power BI: DAX role filter using USERPRINCIPALNAME() — each viewer sees a different slice of the same report.

📌 General: Three regional managers see the same Power BI report but each sees only their region's data — enforced by a DAX filter on the Region table that compares [ManagerEmail] to USERPRINCIPALNAME().

Governance
DLP — Data Loss Prevention

Admin-level policies controlling which connectors can be combined in a single flow. Three categories: Business (can mix with other Business connectors), Non-Business (isolated — cannot mix with Business), Blocked (cannot be used at all). Applied at tenant level (all environments) or environment level (specific environments). Enforced when a flow is saved, not just when it runs.

📌 General: DLP puts Office 365 connectors in Business group and blocks HTTP → nobody can build a flow that reads from SharePoint and POSTs the data to an arbitrary URL — data exfiltration prevented.

🔧 Project: T-Mobile's DLP policies were a constraint the MCP server needed to work around. The solution: the server operates entirely outside Power Platform — it calls Power Platform APIs directly in Python using SSO tokens, bypassing connector/DLP restrictions entirely.

Governance kit
CoE Starter Kit

Center of Excellence Starter Kit — free, open-source set of apps, flows, and Power BI dashboards from Microsoft for governing a Power Platform tenant. Covers: maker activity tracking, app/flow inventory, compliance requests, DLP impact analysis, unused resource cleanup, onboarding new makers. Installed in the Default environment. Takes 4–8 hours to fully configure.

📌 General: An admin installs CoE Kit; within a day they know which 47 apps have 0 active users, which flows error daily, and which makers need DLP training.

🔧 Project: Day 2 of the 7-day plan — the "long pole" task. Deploying and exploring CoE Kit gives you hands-on governance stories for the interview: "I can see all flows in the tenant, identify orphaned apps, and trigger compliance workflows."

Audit
Audit Log

A tamper-evident record of significant actions in Dataverse: who created, updated, or deleted which row, when, using which app. Must be enabled per environment (Settings → Auditing). Admin Center shows high-level analytics; individual table audit history shows row-level changes with old and new values.

📌 General: A compliance officer queries the audit log for all rows deleted from the Contracts table in the past 30 days — who deleted them and when, with the deleted values preserved.

MCP & AI Integration#

Your strongest differentiator. MCP is the plumbing that makes AI assistants actionable. You built the Power Platform layer of this.

Protocol
MCP — Model Context Protocol

An open protocol by Anthropic that standardizes how AI assistants communicate with external tools. The server declares tools as JSON Schema; the client (Claude Code) discovers them via tools/list and invokes them via tools/call. Replaces bespoke AI integrations with a standard interface — like REST was for web APIs. MCP servers can use stdio transport (local subprocess) or HTTP/SSE (remote).

📌 General: Any AI client that implements MCP can use any MCP server — a single standard, many implementations. Like USB: any USB device works with any USB port.

🔧 Project: "I built a local MCP server exposing T-Mobile's Power Platform via 111 tools. The design constraint: no app registration, no admin role, no shared secrets. Users authenticate as themselves via browser SSO and see only what their permissions allow."

Process
MCP Server

A process implementing the MCP protocol that exposes tools to an AI client. Declares tools with name, description (the AI reads this), and inputSchema (JSON Schema). Can run locally (stdio transport — Claude Code launches it as a subprocess) or remotely (HTTP+SSE). Authentication and API calls are the server's responsibility.

📌 General: A GitHub MCP server exposes tools like create_issue, list_pull_requests, get_file_contents — Claude can now manage GitHub without needing the GitHub UI.

🔧 Project: power-platform-mcp-server (Python) exposes 111 tools: Dataverse tools (list_tables, get_rows, create_row), Flow tools (list_flows, run_flow, get_flow_run_history), Solution tools (list_solutions, export_solution). All use SSO bearer tokens.

Transport
stdio Transport

MCP communication method where the client launches the server as a child process and sends JSON-RPC messages via stdin/stdout. Each message is a newline-delimited JSON object. The server writes responses to stdout. Simple, secure (no network port), and the default for local MCP servers. Logs go to stderr so they don't interfere with the protocol.

📌 General: Claude Code's claude.json config specifies the command to launch the server: "command": "python", "args": ["server.py"]. Claude Code forks the process and communicates over stdin/stdout.

🔧 Project: The MCP server uses stdio. Claude Code sends: {"jsonrpc":"2.0","method":"tools/call","params":{"name":"list_tables","arguments":{}},"id":1} on stdin. Server responds with the table list JSON on stdout.

Protocol
JSON-RPC

JSON Remote Procedure Call 2.0 — a lightweight protocol for invoking functions over a transport using JSON messages. Request format: {"jsonrpc":"2.0","method":"tools/call","params":{...},"id":1}. Response: {"jsonrpc":"2.0","result":{...},"id":1}. Error: {"jsonrpc":"2.0","error":{"code":-32602,"message":"..."},"id":1}. MCP uses JSON-RPC 2.0 for all client-server communication.

Callable
Tool (MCP)

A callable function exposed by an MCP server. Defined by: name (string identifier), description (natural language — the AI model reads this to decide when to call it), inputSchema (JSON Schema for parameters with types and required fields). The model reasons about WHICH tool to call and with what arguments; the server owns auth, validation, and the actual API call.

📌 General: get_table_rows tool — description: "Retrieve rows from a Dataverse table with optional OData filter, select, and orderby." The AI calls it automatically when asked "show me all Premium members."

🔧 Project: 111 tools across 4 domains. The most important design decision: descriptions must be precise enough that Claude calls the right tool, but not so wordy that they consume excess context. _resolve_args translates human names to GUIDs before any API call.

Auth
SSO — Single Sign-On

Authentication where one browser login grants access to all connected Microsoft services (M365, Power Platform, Dynamics 365, Azure) via Azure AD OAuth 2.0 tokens. No re-entering credentials. Tokens are short-lived (60–90 min) and refreshed automatically by MSAL.

📌 General: A user logs into their Microsoft account once — they're automatically authenticated in Teams, SharePoint, Power Apps, and Dynamics 365 without additional logins.

🔧 Project: MCP server has no app registration. On first run, it opens a browser for device code flow or interactive auth. The resulting tokens (access + refresh) are cached locally. Every API call uses the current user's token — users only see what their own Azure AD permissions allow. This is the "secure by default" story.

Auth
Bearer Token / JWT

An OAuth 2.0 access token passed in the HTTP Authorization header: Authorization: Bearer eyJ0eXAiO.... Bearer tokens for Microsoft APIs are JWTs (JSON Web Tokens) — base64-encoded signed JSON with claims (upn, scp, aud, exp). Azure AD validates the signature. Tokens expire (60–90 min) and must be refreshed via the refresh token.

📌 General: Paste a bearer token into jwt.io — you can read the decoded claims: your UPN, the scopes granted, the tenant ID, and the expiry time.

🔧 Project: The MCP server acquires tokens via MSAL Python library. Access token is passed in headers["Authorization"] = f"Bearer {token}" for every Power Platform API request. Refresh happens automatically before expiry.

Security
TLS Interception (Zscaler)

Corporate proxies like Zscaler intercept HTTPS traffic by replacing the server's TLS certificate with their own corporate CA. This breaks Python's ssl module (and many other tools) because the Zscaler CA isn't in Python's default certificate bundle — resulting in [SSL: CERTIFICATE_VERIFY_FAILED] errors for all HTTPS requests.

📌 General: On a corporate laptop, curl https://api.example.com works (curl uses OS cert store, includes Zscaler CA), but Python requests.get("https://api.example.com") fails — Python uses its own bundled CA store.

🔧 Project: _tls_bootstrap.py is imported FIRST in the MCP server before any other imports. It detects the Zscaler CA cert from the OS cert store and patches Python's ssl.create_default_context to trust it. This solved the 403/SSL errors blocking all API calls on T-Mobile laptops. This is your best war story — it demonstrates deep debugging under production constraints.

Security design
Read-only by Default

A security design principle where all write operations (create, update, delete) are disabled at startup and must be explicitly enabled per-session. Prevents accidental destructive operations from AI hallucinations or misunderstood commands. Aligns with "principle of least privilege" — start with minimum permissions, grant more only when needed.

📌 General: A database connection library that opens in read-only mode by default — you must call enable_writes() to allow INSERT/UPDATE/DELETE. A developer who only needs to inspect data never risks accidentally mutating production records.

🔧 Project: MCP server starts with all write tools (create_row, update_row, delete_row, delete_solution) disabled. User must explicitly call enable_writes() in the session. This prevents "Claude, show me all loans" from accidentally triggering a delete_row due to a misunderstood command. It's the governance story for an enterprise tool.
