⚠️ The pagination trap — live in this system today#

Two of these months, Nov 2025 and May 2026, exceed Dataverse's 50,000-row aggregate ceiling and return error 0x8004e023. They can only be counted by paginating @odata.nextLink.

Worse: the $count endpoint returns exactly 5000 for nine tables — a capped page size masquerading as a row count. Naively trusted, it would report the hub table as 5,000 rows when it actually holds 186,399. That is a 37× under-count, reported without any error.

This is your STAR 2 story, alive in production, and you can demonstrate it.

3.2The business domain in plain language#

Learn to explain this to a non-technical person in 30 seconds. Consulting interviews test exactly this.

"T-Mobile has facilities across the US where physical access has to be

controlled — who can badge into which building, which doors, which floors,

for how long. The process was heavily manual: requesting a badge, routing it

for manager, building-owner and security approval, assigning clearances,

handling expiry, renewals, terminations, and staying audit-compliant

throughout. At roughly five and a half thousand requests a month — with spikes

past sixty thousand — that doesn't scale manually. I built and ran the Power Platform platform that automates that

lifecycle, and the integrations into the systems that physically open the

doors."

Modelling questions to be ready for#

  • Choice vs lookup — approval status as a choice: fixed small list, stored

as integer, no join. If statuses needed metadata (an SLA duration each), a lookup wins.

  • Why ba_clearancedoor as its own table? Clearance-to-door is

many-to-many with attributes — a junction table with payload, exactly when you don't use a native N:N. Over 5,000 rows mapping 1,851 clearances to doors.

  • Why ba_physicalsecurity carries a PACS choice — one platform, three

target systems, routed by data rather than three parallel codepaths.

  • Alternate keys for idempotency — essential for the CCure bidirectional

sync so a re-run doesn't duplicate personnel records.

  • Why 3,727 clearance-approver rows? Approval authority is per-clearance,

not per-role. That's fine-grained delegation, and it's why the approval routing has to be data-driven.

The bidirectional sync — your best architecture answer#

"The push direction is straightforward: an approved request writes clearances

into the access control system. The interesting direction is the pull. Badge

administrators can and do make changes directly in CCure — it's their primary

tool and there are legitimate emergency cases where they must. If we only

pushed one way, Dataverse would drift out of sync with physical reality and

the audit trail would be wrong, which in a regulated environment is the actual

failure.

So CCure-ManualChangeSync polls on a five-minute cycle, watermarked by a

LastSyncUTC environment variable, picks up changes made directly in CCure,

and reconciles them into Dataverse with every attempt written to a dedicated

sync audit table.

The design principle is that CCure is the system of record for access — it's

what physically opens the door — but Dataverse is the system of record for

process: who requested it, who approved it, when, and why. You need both

directions for the audit story to hold."

This is the single best thing you can say in a technical interview. Systems of record, drift, reconciliation, watermarking, audit.

Loop prevention — expect the follow-up#

"The loop risk is that your push writes to CCure, the poll detects it, writes

it back, triggers another push. You break it by making changes attributable —

you know which identity wrote them — and by comparing state rather than

reacting to events blindly. The watermark handles ordering, but attribution is

what stops the loop: system-originated changes get filtered, human-originated

ones get reconciled."

Testing approach#

Postman collections for QLAB01 (endpoint test, direct URL) and TBadge sync.

"I test integrations outside the platform first. Debug inside Power Automate

and you can't tell whether the problem is your flow or the API. Postman

collections isolate that, and they double as evidence when you escalate to the

API owner."

3.9Your ten STAR stories#

STAR 1 — The submit-button race condition (best "subtle bug")#

Verified from the v374 source. Submitbtn.OnSelect is 61,995 characters / 1,266 lines, of which ~30,684 characters are live code and the rest is commented-out history — including the old varNotify version. Live code contains 3 CountRows(Filter('Badge Process' …)) re-checks, 8 Patch, 11 LookUp, 58 If. varNotify now appears only in comments.

S — Production canvas app, 30 screens, six personas, ~5,500 requests a month in steady state. Users could occasionally submit badge requests that a compliance gate should have blocked — specifically around FTI eligibility, where request type 1000 is the FTI request itself and types 1001/1002 require a qualifying FTI to already exist.

T — Find why the guard wasn't holding; fix it without disrupting live users.

A — The submit button's enablement was driven by a context variable, varNotify, set earlier in the session. If the underlying Dataverse state changed after that variable was set — which happened when approvals moved in another session — the button stayed enabled against stale data. I replaced it with a live Dataverse re-check at submit time: CountRows(Filter(...)) against Badge Process, matching on employee email, employee type, employee ID and request type, excluding Rejected, Revoked, Canceled and Auto-Close-No-Approval statuses. Critically I applied the guard to both Submitbtn.DisplayMode and Submitbtn.OnSelect — because DisplayMode only controls whether the button looks enabled; OnSelect is what executes. Guarding only the visual leaves the race wide open.

R — Blocked submissions were correctly prevented. varNotify survives only as commented-out history in the source. The wider lesson is that in canvas apps a visual guard is not a functional guard — and App Checker flags nine cross-screen event dependencies in that app, the same class of problem: state coupled across screens you can't see from any one of them.

⚠️ If asked about the 62,000-character formula, own it:

"That formula is far too long — about 30,000 characters of live logic plus

another 30,000 of commented-out history. Business rules of that complexity

belong server-side in a flow or plugin where they're testable, not in a

button's OnSelect. They're in the app because of latency — the user needs the

answer before they submit, not after. The right design is a single flow call

returning an eligibility verdict. I'd also delete the commented history;

source control is for history, not the formula bar."

STAR 2 — The silent pagination bug (attention to detail)#

S — Building reporting tooling over Dataverse, I noticed record counts that looked plausible but felt low for the environment.

T — Determine whether the data was genuinely that size or the query wrong.

A — Using $top in the Dataverse Web API suppresses the @odata.nextLink pagination cursor. A query that looked complete returned only the first page, with no error and nothing indicating more data existed. I switched to page-size preference headers with proper nextLink following.

R — Counts corrected. This is the dangerous class of bug — it doesn't crash, it quietly returns incomplete data. A report saying forty records when there are four thousand is worse than an error, because someone will decide on it.

⚠️ This is live in the system today. Querying production, nine tables returned exactly 5000 — a capped page size masquerading as a count. The hub table actually holds 186,399 rows. That is a 37× under-count reported with no error at all. Two individual months also blow past Dataverse's 50,000 aggregate ceiling and can only be counted by pagination. Same bug class, still there, and I can demonstrate it on demand. The canvas equivalent is delegation limits — App Checker flags 75.

STAR 3 — Cross-environment reconciliation (regulated rigour)#

S — A facility compliance attestation dataset — 371 rows — needed to exist correctly across four environments. Production's table was empty; the lower environments were each missing 47 rows.

T — Reconcile accurately without corrupting production.

A — I built comparison tooling to diff the source against each environment rather than eyeballing spreadsheets. Before any destructive change in production I took a full JSON backup of the target table. I wrote a revert guide so the change could be rolled back by someone other than me, and worked through the environments in order with verification at each step.

R — Completed with a documented audit trail and a tested rollback path. In a regulated system the backup and the revert procedure are part of the change, not optional extras — and being the sole vendor resource made that non-negotiable, because there was nobody else to call.

STAR 4 — The vendor escalation (best pure-consulting story)#

S — A new CCure wrapper API was being stood up. Auth and lookup endpoints worked, but POST /v2/personnel consistently returned a 500 with an opaque "General-1000" error.

T — Determine whether the fault was mine or theirs, and unblock.

A — I isolated it away from Power Automate entirely — reproduced it in a standalone Postman collection so the flow wasn't a variable. I verified the request shape against their spec, confirmed auth was valid by calling the working endpoints with the same token, and captured the service-transaction-id from the failing response. Then I escalated with a reproducible collection, the transaction ID, and an explicit statement of what I'd already ruled out.

R — The API team owned it immediately with evidence they could act on, rather than days of back-and-forth about whose side it was on. When you escalate across teams you arrive with the diagnosis already narrowed — it saves time and protects the relationship, which as the only vendor on site I had to actively manage.

STAR 5 — Building the MCP server (initiative)#

S — I was repeatedly doing the same manual investigations: which of fifty flows failed overnight, what differs between STG and PROD, which flows touch this table before a schema change. Each meant maker-portal clicking or a one-off script.

T — Reduce that friction without introducing a security problem.

A — I built a local MCP server exposing Power Platform to an AI assistant — around 111 tools across Dataverse, Power Automate, Power Apps, solutions and security roles. The hard constraint was security: no app registration, no admin role, no shared secrets. Every user authenticates as themselves via browser SSO, so the tool can never do anything the person couldn't already do. Write tools are hidden unless explicitly enabled, raw Dataverse escape hatches need a second flag, everything is audit-logged, and I wrote a threat model.

R — Investigations that took hours took seconds. And it produced the artifact I'm proudest of: the cross-environment comparison that found production was 131 builds behind staging with twelve flows missing. With 50 flows, 25 tables and 55 environment variables across four environments, that analysis wasn't feasible manually. Then I proved the pattern generalised by rebuilding the architecture for UKG Dimensions — a different enterprise API with Boomi middleware.

STAR 6 — Corporate TLS interception (debugging depth)#

S — Nothing could reach any Microsoft endpoint from inside the corporate network — every HTTPS call failed certificate verification.

T — Make it work on corporate-managed machines without disabling TLS verification.

A — The corporate network does TLS interception, so certificates are re-signed by a corporate root CA. Python's bundled certifi store doesn't know that CA, but the Windows certificate store does, because IT pushes it by policy. I patched Python's ssl module at import time to use the OS trust store, so every downstream library — httpx, msal, requests — transparently trusted it. That had to run before anything created an SSL context, so it's the first import in every entry point. Then I found a second failure on other people's machines: stale cert environment variables pointing at deleted virtualenvs were crashing msal before my patch could take effect, so I strip those defensively at startup.

R — Worked on corporate machines with no security compromise — I never disabled verification, I pointed it at the correct trust store. The satisfying part was the second bug, because it only ever affected teammates, never my own machine.

STAR 7 — Requirements shaping (client-facing)#

S — I was the only Accenture person on an all-T-Mobile team. Requirements came from the Enterprise Badging Center administrator, who owned the process and held the admin role.

T — Turn business needs into a working platform without a BA in between.

A — Rather than taking requirements as tickets, I worked through them with her directly — we'd discuss what she actually needed, I'd walk through what was feasible and what the trade-offs were, and we'd reach a conclusion together before I built anything. I'd bring designs back for review and demo working software to the wider team in dedicated calls and standups. Over time that grew into a platform serving six distinct personas across thirty screens with role-based access driven by eleven Entra groups, handling around five and a half thousand requests a month in steady state.

R — She was consistently satisfied with the designs, and rework stayed low because we agreed the shape before I started building. I also trained new joiners on the systems I'd built, so the knowledge didn't sit only with me. Working without a BA layer made me better at asking the second and third question rather than accepting the first framing.

STAR 8 — The N+1 performance fix (engineering judgement)#

S — A clearance comparison view — Dataverse clearances side by side with CCure — was unusably slow and timing out. Production holds 1,851 clearances and over 5,000 clearance-door mappings.

T — Make it usable.

A — Classic N+1: one CCure API call per row. I changed it to bulk-fetch all clearances once and match in memory. I also hit a related problem where long-running builds died on session expiry, so I added a retry of the full build and raised the proxy timeout.

R — The view became usable and timeouts stopped. Standard lesson — when something is slow, count the network calls first. The same instinct shows up in the app: GetTotalRowsCount exists as a flow precisely because the hub table exceeds 50,000 rows and no client-side count can work, and App Checker flags 14 places where CountRows runs over Gallery.AllItems — the same mistake in a different shape.

STAR 9 — Production incident and revert (ownership)#

S — Production issues on flows in a live badging platform — SLA flow behaviour and an attestation data change that needed backing out. This is a system where the urgent-termination flow disables physical building access, so the blast radius is real.

T — Restore correct behaviour without making it worse.

A — My standing practice was to write the revert path before the change. I have documented revert guides for both the SLA flow incident and the attestation change, plus a full JSON backup taken before the destructive step. When issues arose I could roll back to a known state rather than improvising. I documented the defect analyses so the client had the reasoning, not just the fix. The platform has a dedicated integration-status table and a scheduled re-run flow for failed rows, so integration failures were recoverable by design rather than by heroics.

R — Changes were reversible and the client had written procedures they could execute without me. In a regulated environment I treat "how do we undo this" as part of the design.

STAR 10 — The undocumented option set (leaving things better)#

S — Flows across a fifty-flow solution were branching on ba_approvalstatus integers with no documentation of what they meant.

T — Establish the real mapping and stop the guesswork.

A — I worked out the mapping empirically against live data across both tables that use it — Approved, Rejected, Pending, Canceled, Expired-After-SLA — and documented it as a shared reference rather than tribal knowledge.

R — Subsequent flow work referenced a documented mapping instead of magic numbers. Undocumented option sets are a quiet source of bugs: someone hardcodes a value, the meaning drifts, nothing fails loudly. With 631 Dataverse actions across the solution, that ambiguity compounds fast.
