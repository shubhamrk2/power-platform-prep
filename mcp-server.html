PART 02

MCP Server Deep Dive

Your strongest asset: 111 tools, three auth modes, one great war story.

WHY THIS PART MATTERS MOST

This is your single most differentiating asset. Thousands of people can build a Power Automate flow. Almost nobody at 3.5 years has built a 111-tool agent integration layer over an enterprise platform, solved corporate TLS interception, mapped Azure AD pre-authorisation quirks, and shipped it with secure-by-default gating and audit logging.

For the Copilot Studio requirement in the JD, THIS is your answer. Copilot Studio is a product surface for building agents. You built the plumbing that agents run on. That is a deeper understanding, and you should say so.

KNOW THIS MATERIAL COLD. If a technical interviewer goes deep on anything, this is where you want the conversation to go.

2.1What It Is, In One Paragraph#

THE 30-SECOND VERSION (memorise this): "I built a local MCP server that exposes T-Mobile's Power Platform to an AI assistant through the user's own SSO identity. It's about 111 tools covering Dataverse, Power Automate, Power Apps, and solution management. The design constraint that made it interesting was security: no app registration, no admin role, no shared secrets. Every user authenticates as themselves via browser SSO and only ever sees what their own permissions allow. Writes are disabled by default and have to be explicitly enabled."

MCP = Model Context Protocol. An open protocol (from Anthropic) that lets an AI assistant call external tools through a standard interface. A server declares tools with JSON Schema; the client (Claude Code) discovers them and calls them.

IF ASKED "WHAT IS MCP?" ANSWER LIKE THIS:

"It's a standard interface between an AI assistant and external systems. Rather than every integration being bespoke, the server publishes a tool list - each with a name, description, and JSON Schema for its inputs - and the client discovers and invokes them over stdio or HTTP. The value is that the model reasons about WHICH tool to call and with what arguments, while the server owns auth, validation, and the actual API calls. It's essentially function calling with a transport, a discovery mechanism, and a security boundary."

2.3Authentication: Your Best Technical Story#

This is the part that impresses people. Three distinct auth modes, each solving a real problem, plus a genuine Azure AD discovery.

MODE 1: DELEGATED / INTERACTIVE (the default)#

Flow:

  1. First call opens the default browser -> T-Mobile SSO -> normal sign-in

(same experience as opening make.powerautomate.com)

  1. MSAL receives the auth code on a RANDOM localhost port (port=0)
  2. Exchanges code for access + refresh tokens
  3. Persists them ENCRYPTED at ~/.pp-mcp/msal_cache.bin
  • Windows: DPAPI encryption (FilePersistenceWithDataProtection)
  • Other OS: 0600 plaintext fallback (FilePersistence)
  1. Subsequent calls silent for ~90 days via cached refresh token

Code path: acquire_token_silent() first, acquire_token_interactive() fallback.

WHY THIS DESIGN (say this): "I deliberately avoided a service principal for the default path. If I'd used one, every user of the tool would inherit that principal's permissions

  • which is a privilege escalation waiting to happen and an audit nightmare

because every action looks like it came from one identity. With delegated auth, the tool can never do anything the human couldn't already do in the browser, and Dataverse audit logs show the real user."

MODE 2: SERVICE PRINCIPAL / CLIENT CREDENTIALS#

ConfidentialClientApplication with SP_CLIENT_ID + SP_CLIENT_SECRET. In-memory token cache only (audience -> {token, expires_at}), never on disk. 60-second expiry buffer before reuse.

WHY IT EXISTS: some resources are OWNED by a service principal - notably canvas apps and solutions created by an SP account. A delegated user token cannot export them. So there's a fallback path (_is_sp_owner, _bap_headers_sp, _dv_headers_sp) that switches to SP auth for those specific operations.

MODE 3: ROPC (Resource Owner Password Credentials)#

Username/password via acquire_token_by_username_password(). For service-account UPNs (e.g. RSC_DEV_CREBADGE@t-mobile.com) that have MFA disabled or excluded by Conditional Access policy.

BE READY FOR THE PUSHBACK. A sharp interviewer may say "ROPC is deprecated and discouraged." They are RIGHT. Your answer: "Agreed, and it's the last-resort path, not the default. ROPC can't handle MFA at all - it fails with AADSTS50076 - so it only works for service accounts explicitly excluded from MFA policy. I used it for automation against SP-owned resources where the alternative was worse. In a greenfield design I'd use certificate-based client credentials or managed identity instead. The delegated interactive flow is the default and what almost everyone actually uses." Owning that trade-off honestly scores better than defending it.

THE AADSTS65002 DISCOVERY (your single best technical anecdote)#

THE PROBLEM:

Microsoft PRE-AUTHORIZES specific (client_id, API) pairs. You cannot just pick any public client ID and call any API with it.

WHAT YOU FOUND:

PAC CLI's client ID (9cee029c-6210-4654-90bb-17e6e9d36617) is pre-authorized for Dataverse, Power Apps, and BAP - but NOT for service.flow.microsoft.com (Power Automate). Using it there returns AADSTS65002.

Azure CLI's client ID (04b07795-8ddb-461a-bbee-02f9e1bf7b46) has broader pre-authorisation coverage and DOES work for Power Automate.

YOUR SOLUTION:

A per-audience client-ID map: DEFAULT_CLIENT_ID = PAC CLI id

CLIENT_ID_BY_AUDIENCE = {

"https://service.flow.microsoft.com": Azure CLI id } All client apps share ONE token cache, so the user signs in once and every audience works. Overridable via AZURE_CLIENT_ID for tenants with strict Conditional Access.

ALSO NOTED: Azure PowerShell's ID (1950a258-227b-4e31-a9cf-717495945fc2) is blocked by T-Mobile for device-code flow.

HOW TO TELL IT (this is a 90-second story, practise it): "Everything worked except Power Automate, which kept returning AADSTS65002. The error text isn't obvious - it says the client isn't authorised for the resource. What I eventually worked out is that Microsoft pre-authorises specific client-ID-to-API pairs, and the PAC CLI client simply isn't on the allow-list for the Flow API, whereas the Azure CLI client is. So instead of registering my own app - which would have required admin consent I didn't have and wanted to avoid - I built a per-audience client-ID map, sharing one token cache across the client apps. Users still sign in once. That kept the zero-app-registration property intact, which was the whole point."

ERROR CODES YOU DOCUMENTED IN-CODE (know what each means): AADSTS65001 - client needs admin consent in tenant AADSTS65002 - client not pre-authorized for this API AADSTS50011 - redirect URI mismatch AADSTS530034 - Conditional Access; device compliance / VPN issue AADSTS50126 - wrong password (ROPC) AADSTS50076 - MFA required; ROPC cannot handle it AADSTS70011 - invalid scope (your _audience_key guard catches this)

THE _audience_key DEFENSIVE GUARD (shows senior thinking)#

PROBLEM: if a friendly environment name like "CRE_BadgeAutomation_DEV" leaked through without being resolved to its Dataverse URL, the scope became "CRE_BadgeAutomation_DEV/.default" - which AAD rejects with AADSTS70011. Worse: in the INTERACTIVE flow that opens a browser window that can never succeed. The user sits staring at a broken login page.

FIX: validate the audience is an absolute URL and fail fast with a message that names the likely cause (name not resolved via _resolve_args).

WHY THIS IS A GOOD STORY: "I fixed a bug where the failure mode was a browser window that could never succeed. Failing fast with a clear message beats failing slowly with a confusing one." That is a senior instinct - designing the error path, not just the happy path.

2.4Corporate Tls Interception (The Zscaler Problem)#

THE PROBLEM:

T-Mobile's corporate network does TLS interception (Zscaler or similar). Python's bundled certifi trust store has no idea about T-Mobile's corporate root CA. So EVERY https call - login.microsoftonline.com, *.crm.dynamics.com - fails with CERTIFICATE_VERIFY_FAILED / UnknownIssuer.

THE INSIGHT:

The Windows certificate store DOES have the corporate CA - IT pushes it via group policy. The problem is only that Python doesn't look there.

THE FIX (_tls_bootstrap.py): truststore.inject_into_ssl() Monkey-patches Python's ssl module to use the OS trust store instead of certifi. Every subsequent SSL connection - httpx, msal, urllib, requests - transparently trusts the corporate CA.

CRITICAL DETAIL: this must run BEFORE anything creates an SSL context. Hence import _tls_bootstrap is the FIRST import in every entry point, with a # noqa: F401 because linters flag it as unused.

THE SECOND-ORDER BUG YOU ALSO FIXED:

Some user machines had STALE env vars - SSL_CERT_FILE, REQUESTS_CA_BUNDLE, CURL_CA_BUNDLE, SSL_CERT_DIR - pointing at deleted virtualenvs. The requests library (used internally by msal) reads those BEFORE truststore can intercept, and crashes with OSError on the missing path. Fix: defensively delete any of those vars pointing at a nonexistent file, so requests falls back to certifi's path, after which truststore takes over.

WHY TELL THIS STORY:

It shows you can debug across layers - network, TLS, Python import order, third-party library internals - and that you fix problems for OTHER users, not just your own machine. That second-order bug only affected teammates.

ONE-LINER: "Corporate TLS interception meant Python couldn't verify any Microsoft endpoint. The OS trust store had the corporate CA but Python wasn't using it, so I patched the ssl module at import time to use the OS store. Then I found a second failure where stale cert env vars from deleted venvs crashed msal before my patch could take effect, so I strip those defensively."

2.6The Safety Model (Governance Credibility)#

USE THIS WHEN THEY ASK ABOUT DLP/GOVERNANCE. It proves the instinct even though you haven't done tenant DLP.

THREE-TIER GATING (defaults flipped to secure on 2026-05-12 - you hardened it deliberately, mid-project):

Tier 1: READ tools - always available Tier 2: WRITE tools - hidden unless PP_MCP_ALLOW_WRITES=true Tier 3: RAW escape hatches - hidden unless PP_MCP_ALLOW_RAW=true (execute_dataverse_action/function - these can call ANY Dataverse action, so they're the most dangerous surface) Back-compat: PP_MCP_READONLY=true forces both gates off.

IMPLEMENTATION DETAIL WORTH MENTIONING: the gating happens in list_tools() - gated tools aren't merely rejected when called, they're NOT ADVERTISED AT ALL. The model never sees them, so it can't attempt them. That's defence in depth: you remove the capability from the model's world rather than relying on a runtime check.

OTHER CONTROLS

  • dry_run parameter on destructive operations (37 references in server.py)
  • Confirmation gates in guided workflows ("pause and ask the user to confirm")
  • Structured JSON audit logging via _audit() - "never raises", wrapped in

try/except so logging can never break a real operation

  • _truncate_large_fields - prevents huge payloads flooding the model context
  • Post-change verification: release workflow tells you to run

audit_recent_changes afterwards to confirm what actually changed

  • THREAT_MODEL.md - you wrote a formal threat model for your own tool

THE GOVERNANCE SOUNDBITE:

"I applied least-privilege by default. Read tools are always on; write tools are hidden unless explicitly enabled; and the raw Dataverse action/function escape hatches need a separate flag again, because those can call anything. Crucially the gating is at tool-discovery time, not call time - if writes are off, the model never even learns those tools exist. Destructive operations take a dry_run flag, everything is audit-logged as structured JSON, and I wrote a threat model for the tool itself. That's the same thinking DLP applies at tenant level: classify by risk, deny by default, make the dangerous thing require deliberate action."

2.7Name Resolution (_Resolve_Args) - The Ux Design Decision#

THE PROBLEM: Power Platform APIs want GUIDs and full org URLs. Humans (and LLMs) think in names: "the BadgeAutomation solution in DEV."

THE SOLUTION: _resolve_args() accepts friendly names for environments, flows, solutions, connections, and apps, and resolves them to GUIDs/URLs before the API call. GUIDs and full URLs still work.

WHY IT MATTERS FOR AGENTS (good talking point): "If the model has to make three lookup calls before every real call, you burn context and latency and you multiply the chance of a wrong GUID. Resolving names inside the tool means one call does the whole job. Designing tools for an LLM caller is genuinely different from designing them for a human - the tool should absorb the tedium, and the description matters as much as the schema because that's the only documentation the model gets."

RELATED DESIGN CHOICES WORTH MENTIONING

  • Tool DESCRIPTIONS are written as instructions to the model, e.g.

query_dataverse says "Always provide 'select' to keep payloads small" and gives filter syntax examples inline.

  • inputSchema uses defaults and maximums (top: default 50, maximum 5000) to

stop the model requesting unbounded data.

  • _shape / _truncate_large_fields keep responses small enough to be useful.

THIS IS PROMPT ENGINEERING AT THE TOOL BOUNDARY. Say that phrase - it maps directly onto Copilot Studio agent design, where instructions, actions, and knowledge sources are the same problem in a different wrapper.

2.8Bugs You Found And Fixed (All Real, All Defensible)#

  1. BAP /flows RETURNS 0 FLOWS

The Business Application Platform API's flows endpoint only returns flows in PERSONAL scope. Solution-owned flows are invisible there. You had to query Dataverse (the workflows table) instead to get the real inventory. LESSON: know which API is authoritative for which object.

  1. DATAVERSE $top KILLS nextLink

Using $top suppresses the @odata.nextLink pagination cursor, so you silently get only the first page and think that's everything. You have to use page-size preference headers instead for true pagination. THIS IS A GREAT ONE - it's a SILENT correctness bug. "The dangerous bugs aren't the ones that crash, they're the ones that quietly return incomplete data. A report that says 40 records when there are 4,000 is worse than an error."

  1. CCURE PAGINATION WITHOUT _TOTALROWS_

Some CCure instances omit the _TOTALROWS_ field the pagination logic relied on. Fixed to handle its absence. (commit 73353e8) LESSON: never trust an optional field in a vendor API across instances.

  1. CANVAS APP GUID / SOLUTION MAPPING

Canvas app GUIDs don't map cleanly between the app record and the solution component record; download required going via solution export in some cases (_msapp_via_solution_export).

  1. SESSION EXPIRY DURING LONG COMPARE

Long-running side-by-side clearance comparison would die on session expiry. Fixed with retry of the full build plus a raised proxy timeout. (e2f00cc)

  1. N+1 PERFORMANCE FIX

Clearance comparison was making one CCure call per row. Changed to bulk-fetch all clearances once. (85f6061 - a perf commit) CLASSIC N+1. Say it in those words; every senior engineer recognises it.

  1. FTI BLOCKING FIX (canvas app, v358)

Submit button could be enabled against stale state held in a context variable (varNotify). Replaced with a LIVE Dataverse re-check at submit time, applied to BOTH Submitbtn.DisplayMode and Submitbtn.OnSelect. WHY BOTH: DisplayMode controls whether the button LOOKS enabled; OnSelect is what actually runs. Guarding only the visual is a race condition - the user can still trigger it. Guarding both is correct. THIS IS AN EXCELLENT ANSWER to "tell me about a subtle bug you fixed."

  1. THE 8 MCP BUGS (2026-08-05)

You ran a self-audit of your own tool surface and fixed 8 bugs in one pass. Frame as: "I audited my own tooling systematically rather than waiting for users to hit issues."

2.9Likely Deep-Dive Questions On The Mcp Server#

Q: "Why build this at all? Wasn't it out of scope?" A: "It came out of the actual work. I was constantly doing the same things by hand - checking which flows failed overnight, comparing a solution between STG and PROD, finding every flow that touched a given table before a schema change. Each one meant clicking through the maker portal or writing a one-off script. So I built the tool surface once, properly, with auth and safety handled, and then those investigations took seconds. The compounding return was real: the STG-versus-PROD comparison work and the connection reference audits would have been days of manual clicking otherwise."

Q: "How do you handle a tool the model calls with bad arguments?" A: "Three layers. The JSON Schema catches type and required-field errors before my code runs. Then I have defensive guards for the cases schema can't express - _audience_key is the clearest example, where a friendly name instead of a URL would otherwise open a browser window that can never succeed. And third, the tool descriptions are written to steer the model toward correct usage up front - query_dataverse literally tells it to always provide a select clause. Preventing the bad call beats handling it."

Q: "What would you do differently?" A: (Have a real answer - never say "nothing") "Three things. First, server.py is nearly 8,000 lines - it should be split into modules by domain: dataverse, flows, apps, solutions. It grew organically and I'd refactor it now. Second, test coverage is uneven - I have tests around the handoff package but the tool implementations are thinner than I'd like, and they're the part that touches production. Third, I'd drop the ROPC path in favour of certificate-based client credentials; it was pragmatic at the time but it's not what I'd design now."

Q: "How does this relate to Copilot Studio?" A: "Same problem, different layer. Copilot Studio gives you a managed surface - topics, instructions, knowledge sources, actions - and Microsoft handles the orchestration. Building an MCP server means I've implemented the layer underneath: how tools get described so a model picks the right one, how you scope permissions to the calling identity, how you stop an agent doing something destructive. When I design a Copilot Studio agent I'm thinking about tool boundaries and failure modes, not just topic trees. The instinct transfers directly - if anything, understanding the plumbing makes the product surface easier."

Q: "Security review this for me. What's the risk?" A: (They may test whether you can critique your own work.) "The biggest risk surface is execute_dataverse_action and execute_dataverse_function - they're general-purpose escape hatches that can invoke anything the user's permissions allow, so an LLM with a bad plan could do real damage. That's exactly why they're behind their own separate flag beyond the write flag, and hidden from discovery when off. Second risk is token cache theft - it's DPAPI-encrypted on Windows, which ties it to the user account, but on non-Windows it falls back to a 0600 plaintext file, which is weaker. Third is prompt injection: if the model reads Dataverse data containing instructions, it might act on them. The mitigations are the write gating and the confirmation prompts on destructive workflows, but I'd be honest that it's a live concern in any agent system. That's part of why I wrote the threat model."

Q: "Why Python and not C# / PowerShell?" A: "The MCP SDK had a mature Python implementation, MSAL's Python library handles the token cache persistence I needed including DPAPI on Windows, and truststore solved the corporate TLS problem cleanly. PowerShell would have been a more natural fit for a pure Power Platform admin audience, but I needed async HTTP, JSON schema handling, and the MCP protocol layer, and Python was the shortest path to all three."

Q: "What was the hardest part?" A: Use the AADSTS65002 story (section 2.3). It's the best one: real debugging, non-obvious root cause, a constraint you refused to abandon (no app registration), and an elegant fix.

Q: "How many people used it?" A: BE HONEST. If it was mainly you plus a few teammates, say so: "Primarily me, plus teammates I onboarded - which is why I built setup.ps1 as a one-shot installer and why I fixed that stale-cert-env-var bug, since that only ever affected other people's machines, not mine." Do NOT invent an adoption number. If they ask and you inflate it, the follow-up questions will expose it.
