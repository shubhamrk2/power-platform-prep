Why a tenant of your own is the whole point#

You need tenant-level admin. At T-Mobile you were a maker inside someone else's governed tenant — which is precisely why DLP sits as a 🔴 on your scorecard. Only your own tenant lets you author tenant DLP policies, deploy the CoE Kit properly, and create and manage environments.

Microsoft 365 E5 free trial — https://www.microsoft.com/microsoft-365/enterprise/office365-e5

  • 30 days, ₹0 today, full E5 including Power Platform and Dataverse
  • You become global admin of a brand-new tenant
  • Requires a payment method; auto-converts to paid after 30 days
  • You invent the tenant domain: yourname.onmicrosoft.com

A developer tenant has limited Dataverse capacity. Creating four Dataverse environments may exhaust it. If you hit a capacity error:

  • Delete any auto-created trial environments you do not need
  • Use three environments instead of four (put CoE in DEV)

Say this if environment strategy comes up: "In my own tenant I used DEV/TEST/PROD; at T-Mobile it was DEV/STG/UAT/PROD. The principle either way is that production is managed-only and nobody customises directly in it."

7.5Coe Starter Kit: Detailed Walkthrough#

This is the highest-risk lab in the week. Budget the full day. It WILL throw errors - that is expected and is actually the valuable part.

BEFORE YOU START

  • Read the official setup docs first, properly, not skimmed:

https://learn.microsoft.com/power-platform/guidance/coe/setup

  • Download the kit: https://aka.ms/CoEStarterKitDownload
  • Decide which environment it goes in (dedicated COE env, or DEV)

STEP 1 - CREATE CONNECTIONS FIRST

The import will fail or stall if connections do not already exist. Create these in the target environment BEFORE importing:

  • Power Platform for Admins
  • Power Automate Management
  • Power Apps for Admins
  • Dataverse
  • Office 365 Users
  • Office 365 Outlook
  • (others per the current docs - the list changes between versions)

STEP 2 - IMPORT CORE COMPONENTS (MANAGED)

Solutions -> Import solution -> the CoE Core Components managed zip. You will be asked to map connections and set environment variables.

STEP 3 - SET ENVIRONMENT VARIABLES

Typical ones (names vary by version):

  • Admin eMail (your tenant admin address)
  • TenantID (from Azure portal, or pac org who)
  • PowerApps Maker env... (URLs)
  • Various feature toggles

MISSING OR WRONG ENV VARS ARE THE #1 CAUSE OF FLOWS FAILING LATER.

STEP 4 - TURN ON THE INVENTORY FLOWS IN ORDER

The docs specify an order. Do not just enable everything at once. Start with the Admin | Sync Template flows. Run them manually first rather than waiting for the schedule.

STEP 5 - WATCH THEM FAIL, THEN DEBUG

EXPECT: authentication errors, missing env vars, throttling on large tenants, permission errors on the admin connectors. In a small dev tenant there is very little to inventory, so runs are fast - which is an advantage for learning.

FOR EACH FAILURE, WRITE DOWN:

  • Which flow
  • What the error said
  • What the root cause was
  • How you fixed it

THREE OF THESE = your CoE interview answer. This is the deliverable of Day 2, more than the working install.

STEP 6 - EXPLORE WHAT IT BUILT

  • Open the CoE Admin Command Center app
  • Look at the inventory tables: Environment, App, Flow, Maker, Connector
  • NOTICE THE PARALLEL: this is the same inventory your MCP server produces.

Say so in interview - it is a genuinely strong observation.

STEP 7 - OPTIONAL

  • Import Governance Components (adds compliance/approval processes and

DLP Impact Analysis - directly relevant to your DLP gap)

  • Set up the Power BI dashboard if you have Power BI Desktop and time.

SKIP IF SHORT ON TIME - it adds hours and little interview value.

COMMON COE PROBLEMS AND FIXES

"Flow fails with 403" -> the connection identity lacks tenant admin rights; re-create the connection as the global admin account "Env var is blank" -> set it in Solutions > Default > env vars, or via the Setup Wizard app "Import fails on dependency" -> import prerequisite solutions first; read the import log XML, it names the component "Inventory tables empty" -> the sync flows have not run, or ran and failed; check run history, not just the flow's on/off state "Throttled" -> normal on real tenants; rare on a dev tenant

7.6Dlp Lab: Exact Steps#

This converts your weakest scorecard item. Do it carefully.

PART A - CREATE A TENANT-LEVEL POLICY

  1. https://admin.powerplatform.microsoft.com -> Policies -> Data policies
  2. + New Policy. Name it "Tenant Baseline".
  3. Assign connectors to groups:
  • Business: Dataverse, SharePoint, Office 365 Outlook, Teams
  • Non-Business: (leave the default bucket)
  • Blocked: Twitter/X, Dropbox, and similar consumer connectors
  1. SET THE DEFAULT GROUP for new connectors -> choose Non-Business.

UNDERSTAND WHY: Microsoft ships new connectors continuously. Whatever you set as default is where they land automatically. Defaulting to Business is how tenants accidentally allow data egress.

  1. Scope: apply to all environments, or exclude one for the next test.
  2. Save.

PART B - CREATE AN ENVIRONMENT-LEVEL POLICY

  1. New policy, scope it to a SINGLE environment (e.g. DEV).
  2. Make it deliberately different from the tenant policy.
  3. Observe how they combine. KEY LEARNING: the effective policy is the most

restrictive combination - an environment policy cannot loosen what a tenant policy restricts.

PART C - TEST THE ACTUAL IMPACT (this is the bit that gives you a real answer)

  1. In an environment covered by the policy, build a simple flow that uses TWO

connectors currently in the SAME group. Save it. It works.

  1. Now go and move ONE of those connectors to a different group in the policy.

Save and publish the policy.

  1. Go back to the flow. Open it. Try to save it.
  2. OBSERVE AND WRITE DOWN:
  • The flow was not deleted or instantly stopped
  • It fails on save / publish / next run, with a DLP error naming the

violation

  • A running flow does not retroactively die the instant you publish

THIS IS THE DETAIL INTERVIEWERS PROBE. Most people assume DLP kills flows immediately. Knowing the actual behaviour proves you tested it.

PART D - POWERSHELL

  Add-PowerAppsAccount
  Get-DlpPolicy
  Get-DlpPolicy | Select-Object -ExpandProperty displayName
  # Explore New-DlpPolicy and Set-DlpPolicy syntax (read before running)

PART E - THINK ABOUT IMPACT ASSESSMENT

Question to be able to answer: "How do you know what a policy change will break BEFORE you publish it?" Answer: you inventory which apps and flows use the affected connectors and in what combinations. CoE Kit's DLP Impact Analysis does this. Without CoE, you script it against the admin APIs - which is precisely what your MCP server's find_flows_using_connector tool does. TIE THOSE TOGETHER IN INTERVIEW. It is a strong connection.

WHAT YOU CAN HONESTLY SAY AFTERWARDS

"I've authored DLP policies at tenant and environment level in my own tenant, including testing the impact on a live flow - the behaviour people get wrong is that tightening a policy doesn't kill running flows instantly, it fails them on next save or run, which is why impact assessment before publishing matters. What I haven't done is own DLP across a large production tenant with an active maker community and an exception process."

7.8Dataflows / Power Query M Lab#

  1. Create a source file. Make a CSV with ~20 rows of FAKE data - e.g.

EmployeeID, FirstName, LastName, Department, StartDate, Status DO NOT USE ANY REAL T-MOBILE DATA. Invent it.

  1. Power Apps maker portal -> Dataflows -> New dataflow
  2. Choose Text/CSV (or Excel), upload the file
  3. In Power Query editor, perform ALL of these and read the M after each:
  • Promote headers
  • Change column types
  • Remove a column
  • Rename a column
  • Filter rows (e.g. Status = Active)
  • Add a custom column (e.g. FullName = FirstName & " " & LastName)
  • Split a column
  • Group by + aggregate (count per Department)
  • Merge queries (create a second small CSV of Departments and join)
  • Append queries (union two similar tables)
  1. Open Advanced Editor. Read the M:

let Source = Csv.Document(File.Contents("..."), [Delimiter=","]), Promoted = Table.PromoteHeaders(Source, [PromoteAllScalars=true]), Typed = Table.TransformColumnTypes(Promoted, {{"EmployeeID", type text}}), Filtered = Table.SelectRows(Typed, each [Status] = "Active") in Filtered

UNDERSTAND: each step is a named variable referencing the previous one. let ... in defines bindings and returns the final expression. each is shorthand for a single-parameter function, _ is the implicit parameter.

  1. Map the output to a Dataverse table. Choose Load to existing or new table.
  2. Set the KEY COLUMN for upsert. Understand: without a key, you get inserts

and duplicates on every refresh; with one, you get upsert behaviour.

  1. Run the refresh. Check the Dataverse table.

CONCEPTS TO KNOW FOR INTERVIEW

QUERY FOLDING Power Query pushes transformations back to the source as native queries where it can (e.g. SQL WHERE clauses). Folding BREAKS at certain steps - custom functions, some merges, index columns - after which everything is processed locally and performance collapses. You check with "View Native Query". INCREMENTAL Only refresh changed data based on a date column, rather than REFRESH reloading everything. Essential at volume. STANDARD vs Standard dataflows write to Dataverse. Analytical dataflows ANALYTICAL write to Azure Data Lake in CDM format for analytics. DATAFLOW vs Dataflow = scheduled ETL, good for bulk/reference data. FLOW Cloud flow = event-driven, good for per-record business logic. Using a cloud flow for bulk ETL is a classic anti-pattern.

YOUR HONEST FRAME

"My integration work has been API-first - REST and flows, plus Python for bulk reconciliation - rather than dataflow-based. I've since worked through Power Query and M for Dataverse ingestion including query folding and upsert key mapping. The data-modelling instinct transfers; the tool was new to me."

7.11Troubleshooting: When Things Break#

"I can't create an environment - capacity error" -> Dev tenants have limited Dataverse capacity. Delete unused environments. Admin Center -> Resources -> Capacity to see what is consuming it.

"pac auth create opens a browser then fails" -> Check you are signing in with the DEV TENANT account, not your work account. If your machine is domain-joined to T-Mobile, the browser may auto-sign-in with the wrong identity. Use an InPrivate window, or pac auth create --environment <url> --username <devtenant upn>.

"PowerShell: Install-Module is blocked" -> Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser -> Or add -Scope CurrentUser to Install-Module if you lack admin rights

"Get-DlpPolicy returns nothing / access denied" -> You are not tenant admin, OR you are signed in as the wrong account. Run Add-PowerAppsAccount again and check the account. If you are on the Power Apps Developer Plan (not a full tenant), DLP is not available - see the fallback note in SECTION 7.2.

"CoE flows all failing with 403 / unauthorised" -> The connections were created by an account without tenant-wide admin rights. Delete and re-create them as the global admin.

"Copilot Studio: trial not available in my region / tenant" -> Check the tenant region. Dev tenants are typically created in a default region; some previews are region-limited. If unavailable, document what you know conceptually and be honest that you could not get hands-on access.

"Corporate laptop blocks everything" -> DO THIS WORK ON YOUR PERSONAL LAPTOP, as you planned. Do not attempt to install tooling or sign into personal tenants on the T-Mobile/Accenture machine. Beyond the technical friction, it is a policy problem you do not need.

"My dataflow refresh fails on the Dataverse load" -> Usually a type mismatch or a missing required column on the target table. Check that every required (business-required) Dataverse column is mapped.

"I ran out of time"

-> PRIORITY ORDER IF YOU MUST CUT:

  1. KEEP: STAR story rehearsal (Days 6-7) - highest value, always
  2. KEEP: DLP lab - closes your weakest scorecard item, only ~3 hours
  3. KEEP: PAC CLI - quick, explicitly named in the JD
  4. CUT FIRST: Power BI dashboard for CoE
  5. CUT SECOND: Office Scripts
  6. CUT THIRD: the CoE Governance Components (keep Core)
  7. CUT FOURTH: Pipelines lab (you can speak to it honestly without)

7.12Lab Hygiene And Safety Rules#

NON-NEGOTIABLE RULES

  1. PERSONAL LAPTOP ONLY. Never install this tooling or sign into personal

tenants on your T-Mobile or Accenture machine.

  1. NEVER USE REAL T-MOBILE DATA. Not in a dataflow CSV, not in a Dataverse

table, not in a Copilot Studio knowledge source, not in a screenshot. Invent everything. This is a physical security system - the standard is higher than usual.

  1. NEVER COPY T-MOBILE CODE OR SOLUTIONS into your personal tenant. Your MCP

server is a grey area - it is your own code but was built in a work context on a work machine. DO NOT publish it publicly, do not push it to a public GitHub, and do not hand the repo to an interviewer. DESCRIBE it instead. If you want a portfolio artifact, write a sanitised architecture summary with no client identifiers and no code.

  1. NO CLIENT IDENTIFIERS ANYWHERE. No employee names, card numbers, facility

names, internal URLs, service account names, transaction IDs, or tenant GUIDs in anything you produce for the job search.

  1. USE A PASSWORD MANAGER for the dev tenant credentials. You will forget them.
  1. IF YOU SHOW ANYTHING IN INTERVIEW, show your PERSONAL tenant labs - the

CoE install, the DLP policy, the Copilot Studio agent. Never the client's system. Screen-sharing a client's production environment in a job interview would be a serious mistake and interviewers notice.

WHY THIS MATTERS BEYOND COMPLIANCE

How you handle your current client's confidentiality is a live demonstration of how you would handle THEIRS. An interviewer who sees you volunteer restraint - "I'd rather not go into specifics, it's a physical security system, but the pattern was..." - is watching a consultant they could put in front of a regulated client. That is a hiring signal, not an obstacle.

YOU HAVE AN ACTIVE AZURE FREE TRIAL. That unlocks the entire good-to-have Azure column on the JD, and — importantly — it converts your Power Automate Desktop / RPA rating from PARTIAL to a genuinely defensible claim, because you can host an unattended PAD machine on a real VM.

Prerequisites and CLI setup#

Do this once. It gets you authenticated and gives you a single resource group so everything you create is easy to delete in one command later.

powershell

# Sign in with the account that owns the Azure free trial
az login

# Confirm which subscription you are on — make sure it is the trial
az account show --output table

# Create ONE resource group to hold every lab resource.
# Deleting this group later deletes everything and stops all billing.
az group create --name rg-pp-lab --location centralindia

  • az account show confirms you are on the free trial subscription, not a work one
  • Resource group rg-pp-lab created (choose the region nearest you; centralindia for Gurugram)
WRONG-TENANT TRAP. If your laptop is domain-joined, az login may silently pick your Accenture/T-Mobile identity. Check az account show every time. If it is wrong: az logout, then az login --use-device-code and sign in explicitly with your personal trial account.

Lab A — VM for unattended Power Automate Desktop#

This is the highest-value Azure lab because it touches a must-have. The production pattern for unattended RPA is: a cloud flow triggers a desktop flow that runs on a VM with nobody logged in. You are going to build exactly that shape.

STEP 1 — CREATE THE VM

powershell
# B2s is the smallest size that runs PAD comfortably.
# The free-tier B1s (1 GB RAM) is too small — it WILL choke on PAD.
az vm create --resource-group rg-pp-lab --name vm-pad-01 --image Win2022Datacenter --size Standard_B2s --admin-username azureuser --admin-password "<Choose-A-Strong-P@ssword-1>" --public-ip-sku Standard

# Get the public IP you will RDP into
az vm show -d -g rg-pp-lab -n vm-pad-01 --query publicIps -o tsv

STEP 2 — CONNECT AND INSTALL PAD

  • RDP to the public IP (Windows: mstsc) as azureuser
  • Install Power Automate Desktop on the VM (Microsoft Store, or the MSI installer)
  • Install the on-premises data gateway / machine runtime so the VM can be registered to your environment

STEP 3 — REGISTER THE MACHINE (this is the actual skill)

  • In PAD on the VM: sign in with your E5 tenant maker account and register this machine to your environment
  • In the maker portal → Monitor → Machines, confirm the VM appears
  • Create a machine credential (the Windows account the unattended run signs in as) — this is the part people fumble

STEP 4 — TRIGGER IT UNATTENDED

  • Build a trivial desktop flow on the VM (e.g. open Notepad, write a timestamped line, save)
  • Build a cloud flow that runs the desktop flow, choosing the Attended → switch to Unattended run mode against your registered machine
  • Disconnect the RDP session (don't sign out), trigger the cloud flow, and confirm the desktop flow still ran on the VM with no interactive session
THE MOMENT IT STOPS BILLING. When you finish a session, deallocate — az vm deallocate -g rg-pp-lab -n vm-pad-01. "Stopped (deallocated)" means compute billing stops; only the small disk cost remains. Simply shutting down from inside Windows does not deallocate — it keeps billing.
say this

"I've stood up an unattended PAD machine on an Azure VM — registered it to the environment, created the machine credential the unattended run signs in under, and triggered a desktop flow from a cloud flow with no interactive session. So I understand the full unattended chain: VM hosting, machine registration, credential management, and the capacity licensing it needs at scale."

Lab B — Key Vault and secrets in a flow#

Directly relevant to must-have integration and to the "how do you secure credentials?" question (Q67). Near-zero cost — secrets are effectively free.

powershell
# Vault names are globally unique — append something random.
az keyvault create --resource-group rg-pp-lab --name kv-pplab-<yourinitials>01 --location centralindia

# Store a FAKE secret — never a real client credential
az keyvault secret set --vault-name kv-pplab-<yourinitials>01 --name CcureApiKey --value "fake-demo-value-not-real"

# Read it back
az keyvault secret show --vault-name kv-pplab-<yourinitials>01 --name CcureApiKey --query value -o tsv
  • Vault created and the fake secret stored and read back from the CLI
  • In a cloud flow, add the Azure Key Vault connector → Get secret, and pull the value at run time
  • Understand the access model: the connection identity needs an access policy (or RBAC role) granting Get on secrets — without it the connector 403s

CONCEPTS TO KNOW: Key Vault access policies vs RBAC (RBAC is the current default); managed identity as the passwordless way for a VM or app to read a secret; and secret versioning — every set creates a new version and the old one still resolves until you disable it.

say this

"For secrets I default to Key Vault with a managed identity rather than storing credentials in connection references or environment variables — the app reads the secret at run time and nothing sensitive lives in the solution. In my MCP server I gated writes and kept credentials out of the tool surface for the same reason: the secret should never be the thing that leaks."

Lab D — Azure DevOps pipelines#

Azure DevOps is free for up to 5 users and does not consume your Azure credit. This closes the "Power Platform Pipelines vs Azure DevOps" question (Q59) with real experience of both.

  • Create a free org and project at dev.azure.com
  • Install the Power Platform Build Tools extension into the org
  • Create a service connection to your DEV environment using the app registration from the Entra lab (service principal auth)
  • Build a pipeline: Export Solution (from DEV, managed) → publish artifact → Import Solution (into TEST)
  • Run it, watch the solution move, then break it (bad service connection) and read the failure
the model

Power Platform Pipelines = in-product, maker-friendly, zero YAML, but limited customisation. Azure DevOps = full control, gates, approvals, YAML, integrates with the rest of your CI/CD, but heavier to stand up. Small teams / citizen-dev estates → native Pipelines. Enterprise with existing DevOps → ADO. You have now built both, so you can answer from experience, not preference.

Lab E — Networking basics#

Short lab. The JD asks for "networking basics such as service tags and IP allowlisting" — you just need to have touched a Network Security Group and know what a service tag is. Network Security Groups are free.

powershell
# Lock RDP on the Lab A VM down to only YOUR public IP (IP allowlisting)
az network nsg rule create --resource-group rg-pp-lab --nsg-name vm-pad-01NSG --name Allow-RDP-MyIP --priority 300 --access Allow --protocol Tcp --direction Inbound --destination-port-ranges 3389 --source-address-prefixes <your.public.ip>/32

# Example of a SERVICE TAG instead of a raw IP range:
# --source-address-prefixes PowerPlatform
# Service tags are Microsoft-maintained named IP groups, so you allowlist
# "the Power Platform service" without tracking its changing IP ranges yourself.
  • Restricted RDP on the VM to your own IP with an NSG rule
  • Can explain a service tag: a named, Microsoft-maintained set of IP ranges (e.g. PowerPlatform, AzureKeyVault) you reference instead of hard-coding IPs
  • Can explain IP allowlisting: default-deny inbound, then allow only known sources — the same instinct as your DLP default-to-Non-Business call

Lab F — Custom connector (REST)#

A custom connector is a governable, reusable wrapper over an HTTP API that makers consume like any first-party connector. Reuse the Logic App from Lab C as the backend and you get a clean end-to-end story that spans Azure and Power Platform.

  • Maker portal → Custom connectors → New → create from blank (or import an OpenAPI/Postman collection — you already have Postman collections as a reference pattern)
  • General: set host and base URL (point it at your Lab C Logic App endpoint, or a public test API)
  • Security: configure auth — API key, or OAuth2 against your Entra app registration from §7.13
  • Definition: define an action with its request (method, path, headers, body) and response schema
  • Test the operation, then consume the connector from both a cloud flow and a canvas app

CONCEPTS TO KNOW: the OpenAPI (Swagger) definition behind every custom connector; policy templates (e.g. set a header, route to a URL); why a connector is the governance unit — custom connectors are classified in DLP exactly like first-party ones (ties straight back to §7.6), so wrapping an API as a connector is also how you bring it under DLP control.

say this

"I think about custom connectors the way I think about the MCP servers I built — both are about wrapping an enterprise API as a clean, described, governable surface that something else consumes safely. A custom connector gives makers a first-party-feeling action and, crucially, brings the API under DLP classification. At T-Mobile my CCure integration was HTTP-action based; the connector is the same wrapper instinct, packaged for reuse and governance."

Lab G — Custom connector over SOAP#

Power Platform has no native SOAP connector. There are two honest patterns, and knowing which to use is the whole answer to the JD's "SOAP" line.

  1. REST facade (preferred at scale): put a Logic App or Azure Function in front of the SOAP service that accepts JSON, calls SOAP, and returns JSON — then build a custom connector (Lab F) over that facade. Makers never see the SOAP.
  2. Direct HTTP with a hand-built envelope (quick): use the HTTP action with an XML SOAP envelope body, the right Content-Type, and a SOAPAction header, then parse the XML response.

DO THE QUICK ONE to prove the mechanics: point a flow's HTTP action at a public SOAP test service (e.g. a number-to-words or calculator SOAP endpoint).

http
POST http://<public-soap-test-endpoint>
Content-Type: text/xml; charset=utf-8
SOAPAction: "http://tempuri.org/<OperationName>"

<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">
  <soap:Body>
    <OperationName xmlns="http://tempuri.org/">
      <param>value</param>
    </OperationName>
  </soap:Body>
</soap:Envelope>
  • Flow calls a SOAP endpoint with a correct envelope, Content-Type: text/xml, and SOAPAction header
  • Response XML parsed (xpath / xml() expression) into usable fields
  • Can articulate when you'd build the REST facade instead (reuse, governance, hiding SOAP from makers) — this is also Q69
say this

"For legacy SOAP I put a REST facade in front — a Logic App or Function that speaks SOAP outward and JSON inward — and expose that as a custom connector, so makers consume clean JSON and the SOAP and WSDL complexity is contained in one governed place. For a one-off I'll hand-build the envelope in an HTTP action, but the facade is what I'd standardise on."

Lab H — SharePoint integration#

Your E5 tenant includes SharePoint Online. This is the fastest gap to close — and it doubles as the CoE Kit prerequisite awareness (CoE stores some config in SharePoint).

  • Create a SharePoint site, a list with a few columns (FAKE data), and a document library
  • Cloud flow: When an item is created → do something; and Get items / Create item / Create file in the library
  • Canvas app: add the SharePoint list as a data source and read/write to it

CONCEPTS TO KNOW: SharePoint list vs Dataverse table — SharePoint for lightweight/document-centric and where the data already lives in M365; Dataverse for relational integrity, security roles, scale, and business logic. Know the 5,000-item list view threshold and why it bites at volume.

"My production data layer was Dataverse because the domain needed relational integrity and role-based security. I've built on SharePoint lists and libraries in my own lab, including where delegation and the list-view threshold change how you design — so I can make the SharePoint-vs-Dataverse call rather than defaulting to one."

Lab I — Office Scripts#

Small, quick, and closes a named JD item most candidates skip. Office Scripts are TypeScript that run in Excel on the web and are callable from Power Automate.

typescript
function main(workbook: ExcelScript.Workbook) {
  let sheet = workbook.getActiveWorksheet();
  let range = sheet.getRange("A1");
  range.setValue("Updated by Office Script");
  // Return a value so a flow can consume it
  return sheet.getUsedRange().getRowCount();
}
  • Excel on the web → Automate tab → record an action, then read the generated TypeScript
  • Write a script that reads a table, transforms a range, and returns a value
  • Power Automate: Run script action — pass a parameter in, use the returned value downstream

WHEN TO USE: Excel-heavy automation that doesn't justify Dataverse and isn't a desktop-UI job for PAD — e.g. reshaping a spreadsheet a business team lives in. Know that Office Scripts are web-only (not desktop Excel) and share the TypeScript object model with Office Add-ins.
