The 7-Day Plan

Hour by hour, with checkboxes that remember where you got to.

ASSUMPTIONS

  • Full days available (you said you'd give it your all)
  • Working on your PERSONAL laptop
  • Day 8 = build resume, Day 9 = apply
  • Everything below costs ZERO except the optional PL-600 exam fee

WHAT THIS WEEK CAN AND CANNOT DO

CAN: convert DLP and Dataflows from "never touched" to "hands-on at small scale"; convert CoE Kit and Copilot Studio from conceptual to real; make PAC CLI fluent; and - most importantly - make every one of your answers rehearsed, specific, and confident. CANNOT: make you a tenant-scale governance veteran, or get you PL-600. Do not pretend otherwise in the room. See PART 1 SECTION 1.6.

THE SINGLE MOST IMPORTANT THING IN THIS WHOLE PLAN

Day 6-7 (stories and mock interviews) matters MORE than Days 1-5. Technical gaps lose you points. Rambling, unstructured answers lose you the offer. If you run out of time, cut lab work, not rehearsal.

Day 3 - Dlp + Pac Cli + Alm Pipelines#

MORNING (3h) - DLP (converts your weakest item)

  • Power Platform Admin Center -> Policies -> Data policies
  • Create a TENANT-level policy:
  • Move connectors between Business / Non-Business / Blocked
  • Note which connectors are non-blockable
  • Block HTTP and Custom Connectors, then observe what that means
  • Create an ENVIRONMENT-level policy on one environment only
  • TEST THE IMPACT (this is the bit that gives you a real answer):
  • Build a flow using two connectors in the SAME group -> works
  • Move one connector to the other group -> re-open/save the flow
  • Observe: existing flows do NOT break instantly; they fail on next

save/run. THIS IS THE KEY INSIGHT interviewers probe.

  • Read: https://learn.microsoft.com/power-platform/admin/wp-data-loss-prevention
  • Learn the precedence rules: tenant vs environment policy interaction
  • Try the PowerShell cmdlets:
        Get-DlpPolicy, New-DlpPolicy, Set-DlpPolicy

  KNOW COLD:
    - Three groups: Business, Non-Business, Blocked
    - Connectors in different groups CANNOT be used in the same flow/app
    - HTTP and Custom Connectors are the high-risk ones (arbitrary egress)
    - Tenant policies apply broadly; environment policies scope narrower;
      the MOST RESTRICTIVE combination wins
    - Impact assessment before publishing = find affected flows/apps first
      (this is exactly what CoE Kit's DLP Impact Analysis does - tie it back)

AFTERNOON (3h) - PAC CLI fluency

  • pac auth create / list / select / delete
  • pac org who / pac org list
  • pac solution init / add-reference
  • pac solution export --path ./out --name <sol> --managed
  • pac solution unpack --zipfile <zip> --folder ./src

-> LOOK AT THE UNPACKED STRUCTURE. Understand Customizations.xml, solution.xml, the Workflows folder, CanvasApps folder.

  • pac solution pack --folder ./src --zipfile out.zip
  • pac solution import --path out.zip
  • pac solution check (solution checker from CLI)
  • pac admin list / pac admin create-environment
  • pac data export / import

WHY UNPACK MATTERS: source control for Power Platform means unpacked solutions in git. If asked about ALM maturity, this is the answer.

EVENING (2h) - Native Pipelines (closes your stated ALM gap)

  • Set up Power Platform Pipelines in your tenant:

https://learn.microsoft.com/power-platform/alm/set-up-pipelines

  • Create a pipeline DEV -> TEST -> PROD
  • Deploy your Day 1 trivial solution through it
  • Note where connection references and env vars get bound during deploy

NOW YOU CAN SAY: "At T-Mobile our promotions were script-driven and I built tooling around the risky parts. I've since set up native Power Platform Pipelines to deploy through DEV/TEST/PROD, and the validation gates map onto the same failure modes I was guarding against manually."

Day 4 - Copilot Studio + Dataflows/Power Query M#

TIMING NOTE: Copilot Studio is TRIAL-BASED (typically 30-60 days). Activating it today means it is live for interviews over the next month. Do not activate earlier than this.

MORNING (4h) - Copilot Studio (converts a PARTIAL)

  • https://copilotstudio.microsoft.com - start trial in your dev tenant
  • Create an agent. Learn the CURRENT vocabulary properly:
  • AGENT INSTRUCTIONS (the system prompt / persona / rules)
  • TOPICS (trigger phrases + conversation node tree)
  • GENERATIVE ANSWERS (RAG over knowledge sources)
  • KNOWLEDGE SOURCES (SharePoint, websites, Dataverse, uploaded files)
  • ACTIONS (call a connector, a Power Automate flow, or a

custom/REST action)

  • CHANNELS (Teams, web, etc. - deployment surface)
  • AUTHENTICATION (none / Entra / manual)
  • BUILD THIS SPECIFIC AGENT (it maps to your domain, so it demos well):
  1. Create a Dataverse table in your dev env, e.g. a simple request table
  2. Agent with instructions to help users check request status
  3. Add a knowledge source (upload a doc)
  4. Add an ACTION that calls a Power Automate flow which queries Dataverse
  5. Create one custom TOPIC with trigger phrases
  6. Test in the test pane, then PUBLISH to a channel
  • Note the difference between classic topic-based and generative

orchestration - be able to explain when you'd use each

YOUR DIFFERENTIATED ANGLE (rehearse this): "Having built MCP servers, I think about agent design as tool design. The thing that determines whether an agent works isn't the topic tree, it's whether the actions are scoped correctly and described well enough for the model to pick the right one, and whether it can do damage when it's wrong. In Copilot Studio that's action design plus authentication scope; in my MCP server it was tool descriptions plus write gating. Same problem."

AFTERNOON (3h) - Dataflows + Power Query M (converts your other WEAK item)

  • Power Apps maker portal -> Dataflows -> New dataflow
  • Source: an Excel/CSV file (use a simple one you make up - NOT real

T-Mobile data)

  • Load into a Dataverse table
  • In Power Query editor, do these transforms and READ THE M CODE each time:
  • Remove columns, rename, change type
  • Filter rows
  • Merge queries (join)
  • Append queries (union)
  • Group by / aggregate
  • Split column, add custom column
  • Open Advanced Editor. Understand the M structure:

let Source = Excel.Workbook(...), Promoted = Table.PromoteHeaders(Source), Typed = Table.TransformColumnTypes(Promoted, {{"Col", type text}}) in Typed

  • Learn the KEY CONCEPTS for interviews:
  • let ... in structure; each step is a named variable
  • Query folding (pushing transforms to the source - and what breaks it)
  • Incremental refresh
  • Standard vs analytical dataflows
  • Dataflow -> Dataverse table mapping, key column for upsert
YOUR HONEST FRAME:

"My integration work at T-Mobile was API-first - REST calls and flows, plus Python for bulk reconciliation - rather than dataflow-based. I've since worked through Power Query and M for Dataverse ingestion, including query folding and upsert key mapping. The modelling instinct transfers; the tool is new to me."

EVENING (2h)

  • Model-Driven App gap (JD asks for it, your evidence is thin):
  • Build ONE model-driven app over your Dataverse table
  • Configure: a form, a view, the sitemap, one business rule
  • Understand when MDA beats Canvas: data-dense, role-based, standard CRUD,

auto-responsive, security-role-driven; Canvas wins for bespoke UX, non-Dataverse sources, pixel control

  • Adaptive Cards gap (also in the JD):
  • Use https://adaptivecards.io/designer
  • Post one Adaptive Card to Teams from a Power Automate flow
  • Understand: JSON schema, Action.Submit, actionable approvals in Teams

Day 5 - Remaining Gaps + Self-Audit#

MORNING (3h) - The gaps you can only speak to, not close

  • SOAP: read up on how Power Platform consumes SOAP (custom connector with

a SOAP pass-through, or Logic Apps). Know that WSDL defines the contract, that it's XML-envelope based, and that most modern work wraps SOAP behind REST. HONEST LINE: "I haven't consumed SOAP directly in Power Platform; my integration work was REST. I understand the model and I'd expect to wrap it in a custom connector or use Logic Apps for the heavier cases."

  • Office Scripts: read the basics (TypeScript in Excel online, called from

Power Automate via the Excel Online connector, Run Script action). Try ONE trivial script if you have Excel online in your dev tenant.

  • Power Automate Desktop: BE PRECISE about what you have done.
  • If ATTENDED only: say attended. Learn what unattended requires:

machine groups, gateway, credentials in the machine, unattended RPA licence/capacity add-on, queue-based work distribution, error handling.

  • Build one small desktop flow today so it's current in your mind.
  • Azure good-to-haves - read only, 20 min each: Key Vault (secret storage,

referencing from Logic Apps/custom connectors), Logic Apps vs Power Automate (same engine, different licensing/governance/scale story), Azure DevOps pipelines for Power Platform (Power Platform Build Tools), service tags and IP allowlisting.

AFTERNOON (3h) - Repo self-audit (so nothing surprises you)

  • Re-read your own THREAT_MODEL.md
  • Re-read auth.py end to end - you will be asked about it
  • Skim server.py's _all_tools() so you can speak to the tool surface
  • Re-read your revert guides and one defect analysis
  • Make a ONE-PAGE cheat sheet of numbers (commits, LOC, tool counts, tables,

environments) - PART 1 SECTION 1.2 has them all

EVENING (2h) - Sanitisation pass (IMPORTANT)

  • Decide exactly what you will and will not say about T-Mobile's system
  • Never: employee names, card numbers, facility lists, internal URLs,

credentials, specific security weaknesses

  • Always: "the EBC administrator" not a person's name
  • Prepare the deflection line: "I'd rather not go into specifics since it's

a physical security system, but the pattern was..."

  • If you plan to show ANY code/screens in interview, sanitise it first, or

better: don't. Describe instead.
