Parent / Child flows — what interviewers probe

Q: How does a parent flow call a child flow?
A: Parent uses connector Flows → action "Run a child flow". Child uses trigger "Manually trigger a flow" with defined typed inputs. Both flows must be in the same Dataverse solution (solution-aware). Child returns data to parent via the "Respond to a PowerApp or flow" action at the end.

Q: Can a child flow call another child flow?
A: Yes — up to 5 levels of nesting. Each must be a separate solution-aware cloud flow.

Q: "Start and wait for an approval" vs "Create an approval" — when do you use each?
A: Start and wait is BLOCKING — the flow execution pauses (up to 30 days) until a human responds; next steps use the outcome directly. Create an approval is non-blocking — flow moves immediately to the next step; you check the result later with "Wait for an approval". Use non-blocking when you want to send parallel approval requests to multiple people simultaneously, then aggregate responses.

Q: How do you set a Lookup column in a "Create a new row" or "Update a row" action?
A: The field name must end with @odata.bind and the value must be /tableplural(GUID). Example: field = toh_request@odata.bind, value = concat('/toh_requests(', triggerBody()['RequestId'], ')'). Passing just the GUID gives "Invalid argument — lookups require OData bind".

Q: Why can't a child flow access the parent's variables?
A: They are separate flow run instances with isolated execution contexts. All data must be passed explicitly as declared inputs on the child's "Manually trigger a flow" trigger. If you forget to declare an input, the "Run a child flow" action won't show it as a field to populate.

PROJECT TRACK — DAY 3: DLP Proof + First ALM Deployment (DEV→UAT)

Create the DLP policies that govern TechOpsHub, then deploy the solution managed to PP-UAT via PAC CLI and Power Platform Pipelines. This is the single most interview-relevant day for governance architecture questions.

DLP — Tenant-level policy "TechOps Standard"

  • Business group (connectors that can work together): Office 365 Outlook, Microsoft Teams, Approvals, Dataverse, SharePoint, OneDrive, Office 365 Users
  • Non-Business: HTTP, SQL Server, Azure Blob Storage
  • Blocked: All custom connectors (default)

DLP — Environment-level policy on PP-DEV only: "TechOps DEV Override"

  • HTTP connector → moved to Business group
  • Scope: PP-DEV environment only
  • Effect: DEV can use Outlook + HTTP in the same flow (for raw API testing); UAT/PROD cannot

The DLP test that creates your war story

  1. In PP-DEV: build a flow using Outlook (Business) + HTTP (Business via override) → it saves and runs
  2. Now auth to PP-UAT and try to save the same flow → it fails with DLP violation
  3. The key insight: tenant policy applies everywhere; the environment override only loosens it in DEV. The most restrictive combination wins. This is exactly what interviewers probe.
