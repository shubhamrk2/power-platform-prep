5.3Power Platform Technical: Dataverse#

Q18: "Explain the difference between a choice column and a lookup."#

Know this
Choice/option set = fixed list stored as integer, defined in schema, fast, no join, but changing options is a schema change and it's not data-driven. Lookup = relationship to another table row, extensible at runtime, supports referential integrity and extra attributes on the target, but requires $expand to read and adds a join. YOUR ANGLE: "I worked with ba_approvalstatus, an eight-value option set shared across two tables. It was the right call for a fixed workflow status. If those statuses had needed extra metadata - SLA duration per status, say - a lookup would have been better."

Q19: "What's the difference between a business rule, a business process flow,#

a plugin, and a Power Automate flow?" [KNOW] Business rule - declarative, runs client and/or server side, simple field logic (show/hide, require, set value, validate). No code. BPF - guided multi-stage process across records; adds a table. Plugin - C# server-side, registered on a message/stage in the pipeline, synchronous or async, full transaction control. Use for: real-time validation, complex logic, transactional integrity, performance-critical. Cloud flow - low-code, async, connector-rich, easy integration, but latency and throughput limits and licensing per connector. RULE OF THUMB: real-time + transactional + performance => plugin. Integration + orchestration + human approval => cloud flow. Simple field behaviour => business rule.

Q20: "When would you use a real-time (synchronous) workflow vs asynchronous?"#

Know this
Sync when the user must see the result immediately or the operation must roll back with the transaction. Async for anything slow, or that calls out to external systems, because you never want an external API in a user's save transaction.

Q21: "Explain the Dataverse plugin execution pipeline."#

Know this
Stages: PreValidation (10, outside transaction), PreOperation (20, inside transaction, before the main op), MainOperation (30, platform), PostOperation (40, inside transaction, after). Sync vs async registration. Know: PreValidation runs before security checks in some cases and outside the transaction, which is where you do cheap rejections.

Q22: "How do you handle bulk data operations in Dataverse?"#

Know this
Batch requests ($batch / ExecuteMultiple), which your MCP server exposes as batch_dataverse. Dataflows for ETL-style loads. Bulk delete jobs. Be aware of API service protection limits: requests per user per 5 min, execution time, concurrency - and that 429 responses carry a Retry-After header you must honour. YOUR ANGLE: mention the 371-row cross-environment reconciliation and the $top pagination bug (PART 3 STAR 2).

Q23: "What are alternate keys and why do they matter for integration?"#

Know this
A non-primary unique key on a table (e.g. an external system's ID). They enable UPSERT by that key, which is the foundation of idempotent integration - you can re-run a sync without creating duplicates. YOUR ANGLE: directly relevant to the CCure bidirectional sync.

Q24: "How does Dataverse security work?"#

Know this
Layers: business units -> security roles -> privileges (Create, Read, Write, Delete, Append, AppendTo, Assign, Share) -> access levels (None, User, Business Unit, Parent:Child BU, Organisation). Plus record-level sharing, teams (owner/access/Entra-group), field-level security for individual columns, and hierarchy security. YOUR ANGLE: your MCP server has list_security_roles, assign_role, revoke_role, grant_record_access, revoke_record_access - you built against this model.

Q25: "What's the difference between an owner team, access team, and Entra group#

team?" [KNOW] Owner team can own records and has roles. Access team is dynamic, used for record sharing at scale, cannot own records. Entra/AAD group team syncs membership from Entra ID - membership managed outside Dataverse.

Q26: "Explain solution layering."#

Know this
Base layer (system) -> managed solution layers in install order -> unmanaged layer on top (always wins). An unmanaged customisation over a managed component blocks managed updates to that property - the classic "why didn't my update take" problem. Remove the unmanaged layer to restore. YOUR ANGLE: your get_solution_layers tool exists precisely for diagnosing this.

Q27: "Managed vs unmanaged solutions?"#

Know this
Unmanaged = development, components editable, deleting the solution doesn't remove components. Managed = deployment, components locked (except where the publisher allowed customisation), uninstall removes components cleanly. Rule: dev unmanaged, everything downstream managed.

Q28: "What is a publisher and why does the prefix matter?"#

Know this
Publisher defines the customisation prefix (yours was ba_) and the option-value base. Prefix is baked into schema names permanently - changing it later means recreating components. Set it correctly on day one.

Q29: "How do you do a soft delete / audit trail in Dataverse?"#

Know this
Native auditing (per-table and per-column, with retention config), statecode/statuscode for logical deletion, or a dedicated audit table. YOUR ANGLE: you produced CCure_Sync_Audit_Log_Import.xlsx and structured audit logging in the MCP server - audit was a first-class concern in your domain.

Q30: "What's the difference between FetchXML and OData/Web API?"#

Know this
FetchXML: Dataverse-native XML query language, supports aggregation, grouping, complex link-entity joins, and is what saved views use. OData/Web API: REST standard, easier for external consumers, supports $select $filter $expand $top $orderby, but weaker on aggregates and deep joins. YOUR ANGLE: your server exposes BOTH (run_fetchxml and query_dataverse) precisely because each wins in different cases.

5.4Power Platform Technical: Canvas And Model-Driven#

Q31: "Canvas vs model-driven - when do you choose which?"#

Know this
Canvas: bespoke UX, pixel control, non-Dataverse or multi-source data, task-focused, mobile-first, process-guided. Model-driven: data-dense, standard CRUD, security-role-driven, auto-responsive, metadata-driven, faster to build when the data model IS the app. HONEST ADD: "My production work has been Canvas-first because the badge request journey needed a guided, opinionated UX. I've built model-driven apps and I'd reach for one when the app is essentially a well-secured view over a data model."

Q32: "What is delegation in canvas apps and why does it matter?"#

Know this
THIS IS THE MOST COMMON CANVAS INTERVIEW QUESTION. Delegation means the filter/sort is pushed to the data source rather than pulled into the app. Non-delegable operations only process the first N records (default 500, configurable to 2000), so you get SILENTLY WRONG results on large tables. Delegable in Dataverse: =, <>, <, >, StartsWith, And/Or/Not, sorting on most columns. NOT delegable: Search() on some sources, in operator in many cases, complex expressions, most functions applied to the column side. Blue underline warning in the editor flags it. YOUR ANGLE: tie to STAR 2 - "silently incomplete data is the dangerous class of bug; delegation limits are the canvas version of the pagination bug I hit in the Web API."

Q33: "Explain the difference between Collect, ClearCollect, Set, and UpdateContext."#

Know this
Set = global variable, app-wide. UpdateContext = context variable, scoped to one screen. Collect = append to a collection. ClearCollect = replace a collection. Also Patch for writing to a data source, and With() for scoped local values. YOUR ANGLE: your race condition (STAR 1) was exactly a stale context variable
  • varNotify - being trusted instead of re-reading source state.

Q34: "How do you optimise a slow canvas app?"#

Know this
Reduce OnStart work and use concurrent (Concurrent()); avoid loading entire tables; use delegable queries; minimise controls per screen; avoid nested galleries; use With() to avoid recomputation; set ExplicitColumnSelection; delay-load screens; avoid volatile functions in loops; use named formulas (App.Formulas) for cached derived values.

Q35: "What's the difference between DisplayMode and OnSelect for a button?"#

Know this
DisplayMode controls appearance/interactivity (Edit/View/Disabled). OnSelect is the behaviour that runs. A guard in DisplayMode alone is a VISUAL guard, not a functional one. YOUR ANGLE: this IS your STAR 1. Tell it here.

Q36: "How do you handle errors in a canvas app?"#

Know this
IfError(), IsError(), Errors() on a data source, Notify() for user messaging, and the newer error-handling behaviours. Patch results should be checked, not assumed.

Q37: "How do you version and roll back a canvas app?"#

Know this
Version history in the maker portal, restore to prior version, publish vs save distinction (saving doesn't publish to users). YOUR ANGLE: your MCP server has list_canvas_app_versions, restore_canvas_app_version, publish_canvas_app - you automated this.

Q38: "What is a .msapp file?"#

Know this
The canvas app package - a zip containing the app definition, controls, and formulas as JSON/YAML. Can be unpacked (pac canvas unpack) for source control and diffing. YOUR ANGLE: you built search_canvas_app_formulas by unpacking msapp and extracting properties - i.e. you can grep Power Fx across an entire app, which the portal cannot do. That is a genuinely impressive detail.

Q39: "How do you source-control a canvas app?"#

Know this
pac canvas unpack to YAML/JSON, commit that, pack on the way back. Acknowledge it's imperfect - merge conflicts in canvas source are painful.

Q40: "What are component libraries?"#

Know this
Reusable canvas components shared across apps, versioned, with custom input/output properties. Good for design-system consistency across a client's app estate.

5.5Power Platform Technical: Power Automate#

Q41: "Walk me through the trigger types."#

Know this
Automated (event, e.g. Dataverse row created/modified), Instant (manual/ button/PowerApps V2), Scheduled (recurrence), Business process flow triggers, and HTTP request trigger (When an HTTP request is received). Desktop flows for

RPA.

Q42: "How do you handle errors and retries in a cloud flow?"#

Know this
Configure run-after (has failed / has timed out / is skipped) on actions, Scope + Try/Catch/Finally pattern, retry policy per action (default, none, fixed interval, exponential), Terminate action with status, and error handling on the connector level. Log failures to a table for observability. YOUR ANGLE: mention your find_failed_runs_in_env and export_flow_failed_runs_to_excel tooling - you built failure observability.

Q43: "How do you handle concurrency in flows?"#

Know this
Concurrency control on triggers (degree of parallelism, default 25 for some triggers), Apply to each concurrency setting, and the trap: parallel execution plus shared state causes race conditions. Set concurrency to 1 when order matters.

Q44: "What are the throttling limits and how do you design around them?"#

Know this
API request limits per user per 24h by licence, Dataverse service protection limits (requests per user per 5 min, concurrency, execution time), connector-specific limits. Design: batch operations, avoid per-row API calls (N+1), use pagination properly, honour Retry-After on 429. YOUR ANGLE: STAR 8, the N+1 fix.

Q45: "Child flows - when and why?"#

Know this
Reuse, separation of concerns, and independent error handling. Must be in a solution, called via "Run a Child Flow", and there are licensing/connection considerations (child flow runs in the context of its own connections).

Q46: "How do you pass data between flows?"#

Know this
Child flow input/output, HTTP request/response, Dataverse rows as a queue, Service Bus for real decoupling.

Q47: "What is a connection reference and why does it exist?"#

Know this
It decouples a flow from a specific connection instance so the same solution can bind to different connections per environment. Without them, importing a solution ties flows to the importer's connections. YOUR ANGLE: THIS IS YOUR TERRITORY. You wrote extract_connrefs.ps1, analyze_crefs.py, bind_connection_reference, and a whole PROD connection analysis. Say: "Connection references and environment variables are where Power Platform ALM actually breaks - not the solution package. That's why I built tooling to extract, compare, and rebind them."

Q48: "Environment variables - definition vs value?"#

Know this
The DEFINITION ships in the solution; the VALUE is environment-specific. Classic mistake: exporting with the dev VALUE included, which then overwrites the target's value on import. Best practice: ship definitions, set values per environment (or via pipeline/deployment settings file). YOUR ANGLE: your sync_env_vars tool with dry_run.

Q49: "How do you debug a failed flow run?"#

Know this
Run history -> failed action -> inputs/outputs -> error message; resubmit; check trigger conditions; check connection auth expiry; check throttling (429); check for null references from an upstream action that returned nothing. YOUR ANGLE: you built /diagnose-failed-run as a guided workflow and get_flow_run_details with large-field truncation.

Q50: "What's the difference between Power Automate and Logic Apps?"#

Know this
Same underlying engine. Power Automate: business-user oriented, per-user/ per-flow licensing, lives in Power Platform governance (DLP, environments, solutions). Logic Apps: Azure resource, consumption or standard pricing, ARM/ Bicep deployable, better for high-throughput integration, VNet integration, and developer-owned CI/CD. Rule: business process => Power Automate; system integration at scale => Logic Apps.

Q51: "How would you implement an approval that can be actioned from Teams,#

Outlook, AND a custom app?" [KNOW] THIS IS A TRAP QUESTION AND YOU HAVE REAL EXPERIENCE WITH IT. The Approvals connector has no "respond" action and no triggers you can use to intercept a response, so a UI-driven approval path and a Teams/Outlook Approvals path are structurally hard to unify - you end up with two sources of truth. YOUR HONEST ANSWER: "I hit exactly this at T-Mobile. The Approvals connector is a closed loop - you can create an approval and wait for it, but you can't respond to one programmatically, and there's no trigger on response you can hook. So if you also let people approve in a custom app you get two routes writing to the same state with no coordination. The clean design is to make your own Dataverse table the single source of truth for approval state, use Adaptive Cards in Teams with Action.Submit posting back to a flow that writes to that table, and never use the built-in Approvals connector as the system of record. I documented that conclusion because an earlier proposed fix on our side was wrong." THIS ANSWER WILL IMPRESS. It's specific, hard-won, and shows you correct earlier bad decisions.

Q54: "How do you move reference/config DATA between environments?"#

Know this
Configuration Migration Tool (schema + data), dataflows, or scripted upsert via alternate keys. YOUR ANGLE: the 371-row attestation reconciliation - you did this with tooling and pre-change backups.

Q55: "Explain DLP policies."#

Know this
MUST KNOW COLD - this is your weak area so over-prepare it.
  • Three groups: Business, Non-Business, Blocked.
  • Rule: connectors in DIFFERENT groups cannot be combined in the same flow or

app. Blocked connectors can't be used at all.

  • Scope: tenant-level (applies broadly, can exclude/include environments) and

environment-level. Where multiple apply, the most restrictive wins.

  • Default group setting governs where NEW connectors land - important, because

Microsoft ships new connectors continuously.

  • Custom connectors can be classified, and by pattern/URL in newer tooling.
  • HTTP and Custom Connector are the high-risk ones: arbitrary data egress.
  • IMPACT: tightening a policy does NOT instantly kill running flows. They fail

on next save/publish/run. THIS IS THE DETAIL INTERVIEWERS PROBE.

  • Impact assessment before publishing: identify affected apps/flows first.

CoE Kit has a DLP Impact Analysis component that does exactly this.

  • Cmdlets: Get-DlpPolicy, New-DlpPolicy, Set-DlpPolicy, Remove-DlpPolicy.

Q56: "How would you design DLP for a client starting from scratch?"#

Say this
"I'd start restrictive and open deliberately rather than the reverse, because loosening is easy and tightening breaks things. Concretely: a tenant baseline policy where the default group for new connectors is Non-Business, so anything Microsoft ships lands somewhere safe. Block the genuinely dangerous ones outright unless there's a case - HTTP and unclassified custom connectors especially, since those are arbitrary egress. Then environment-level exceptions rather than tenant-wide loosening: a developer environment or a specific integration environment can have a broader policy, contained. Before any change goes live, run an impact assessment - find which apps and flows would break, because tightening doesn't fail loudly, it fails on next run. And I'd pair it with a documented exception process, because a policy with no route to 'yes' just drives people to shadow IT."

  • Core Components: inventory of environments, apps, flows, makers, connectors

via sync flows into Dataverse; Command Center app; Power BI dashboard.

  • Governance Components: compliance processes, app archival/cleanup, DLP

impact analysis, approvals for high-risk resources.

  • Nurture Components: maker onboarding, training, app catalogue, champions.
  • Audit Log connector for usage telemetry.

Prerequisites: service account or app registration with tenant-wide read, premium licences, and a dedicated environment. YOUR ANGLE: after Day 2, you can speak to the actual install experience.

Q58: "How do you decide environment strategy for a client?"#

Say this
"It depends on the size of the maker community and the risk profile, but the shape I'd argue for is: personal productivity environments for citizen makers with a restrictive DLP policy; a shared dev environment per project or product team; then test/UAT and production per product line, all managed-only. Production locked down so nobody can make direct customisations. The two things that matter most are naming conventions - because you cannot govern what you can't identify - and default environment lockdown, because the default environment is where ungoverned sprawl accumulates by design."

Q59: "Power Platform Pipelines vs Azure DevOps - which and why?"#

Know this

5.7Integration And Architecture#

Q62: "How do you integrate Power Platform with an external REST API?"#

Know this
Options in order of governance-friendliness:
  1. Certified/standard connector if one exists
  2. Custom connector (OpenAPI/Swagger definition, auth config, policies)
  3. HTTP action (premium, but bypasses connector governance - DLP treats it as

high risk for exactly this reason)

  1. Azure API Management / Logic Apps in front for heavier needs

YOUR ANGLE: the CCure integration - a wrapper API in front of the vendor system, tested independently in Postman.

Q63: "Why put a wrapper API in front of a vendor system?"#

Say this
(You lived this.) "Several reasons. It gives you a stable contract when the vendor's API isn't one - we hit differences BETWEEN INSTANCES of the same product, like pagination metadata being present in one and absent in another. It's a place to centralise auth so credentials aren't spread across flows. It lets you shape responses for the consumer rather than passing vendor quirks through. And it's a governance boundary - one reviewable integration point rather than many."

Q64: "How do you make an integration idempotent?"#

Know this
Alternate keys + upsert; idempotency keys on the request; dedupe windows; check-then-act with a unique constraint rather than relying on read-then-write. YOUR ANGLE: bidirectional sync makes this essential - you don't want the polling flow re-creating what the push flow just wrote.

Q65: "How do you handle bidirectional sync without loops?"#

Say this
STRONG QUESTION FOR YOU. "The loop risk is that your push writes to system B, B's change is detected by your poll, and you write it back to A, which triggers another push. You break it by making changes attributable - stamping the writing identity or a correlation ID so the polling side can ignore changes it caused - and by comparing state rather than reacting to events blindly. In the CCure case the polling flow was there specifically to catch MANUAL changes made by administrators directly in the access control system, so the discriminator matters: system-originated changes get filtered, human-originated ones get reconciled."

Q66: "What's your approach to API pagination?"#

Know this
Follow the vendor's cursor mechanism; never assume a total-count field exists; verify against a known total when you can; treat 'no more pages' and 'error mid-pagination' as different outcomes. YOUR ANGLE: BOTH your pagination war stories - $top killing @odata.nextLink in Dataverse, and CCure instances omitting _TOTALROWS_. Two different systems, same class of bug. That's a great point to make.

Q67: "How do you secure credentials in an integration?"#

Know this
Never in the flow definition. Environment variables of type Secret backed by Azure Key Vault; connection references with proper auth; managed identity where supported; service principal with certificate over secret. YOUR ANGLE: your MCP server keeps SP tokens in memory only, never on disk, and DPAPI-encrypts the delegated token cache. And you wrote a threat model.

5.11Power BI (PL-300 / Accenture P4)#

Know this
Power BI comes up for this role because "Emerging ERP Solutions" (Deloitte) bundles Power BI with the Power Platform practice. Be ready for it even though it isn't your deepest area. Honest frame: "My production work was Dataverse, apps, flows and integration rather than BI reporting — but the foundations transfer directly: I know relational modelling and I've used Power Query for Dataverse ingestion. I'm working through PL-300 to formalise the visualisation and DAX layer." Then answer the technical questions cleanly below.

Q80: "Explain datasets, reports, and dashboards in Power BI."#

Know this
A dataset (now "semantic model") is the prepared, modelled data — tables, relationships, measures. A report is one or more pages of interactive visuals built on a dataset. A dashboard is a single Service-only canvas of pinned tiles, often from several reports, for an at-a-glance summary. One dataset can feed many reports; dashboards exist only in the Power BI Service, not in Desktop.

Q81: "Import vs DirectQuery — when each?"#

Know this
Import caches a copy of the data in Power BI's in-memory engine (VertiPaq) — fast, full DAX, but refreshed on a schedule. DirectQuery leaves data in the source and queries live — always current and good for very large or compliance-bound data, but slower and with DAX/modelling limits. Default to Import; reach for DirectQuery when data is too big to cache, must be real-time, or must not leave the source. Composite models mix both.

Q82: "Measure vs calculated column?"#

Know this
A calculated column is computed row-by-row at refresh, stored in the model, and uses row context — good for a per-row attribute you slice by. A measure is computed at query time, not stored, and responds to filter context — it recalculates for whatever the user has selected. Rule: aggregations/totals that must react to slicers → measure; a fixed per-row value → column. Overusing calculated columns bloats the model; prefer measures.

Q83: "What is a star schema and why use it?"#

Know this
A central fact table (the measurable events — sales, transactions) surrounded by dimension tables (the descriptors — date, product, customer, region), linked one-to-many. Power BI's engine is optimised for it: simpler DAX, faster queries, cleaner filtering than a "flat" or snowflaked model. A dedicated Date dimension is standard so time-intelligence functions work. This is the single most important modelling idea in BI — and it's the same relational thinking as your Dataverse work.

Q84: "What is row-level security and how do you implement it?"#

Know this
RLS restricts which rows a user sees in the same report. You define roles with a DAX filter on a table (e.g. [Region] = USERPRINCIPALNAME() via a mapping table for dynamic RLS, or a static filter per role), then assign users/groups to roles in the Service. It filters data, not visuals — to hide whole pages you use other means. Tie-in to your strength: "It's the same instinct as Dataverse security roles and the write-gating I built into my own tooling — least privilege at the data layer."

Q85: "How does Power BI relate to Dataverse and the Power Platform?"#

Know this
Power BI is the analytics member of the Power Platform family, sharing the same Power Query engine and connectors. It reads Dataverse natively (Dataverse connector, or "Analyze in Power BI" from a model-driven app). You can embed Power BI tiles in canvas and model-driven apps, and trigger flows from Power BI data alerts. So the pattern is: Dataverse as the system of record, apps for capture, flows for process, Power BI for the read/insight layer on top.

Q86: "Power BI dataflows vs Power Platform dataflows?"#

Know this
Both are Power Query in the cloud. Power BI dataflows write to Azure Data Lake / the BI workspace and feed datasets. Power Platform dataflows write to Dataverse tables (what you'd use to ingest into an app's data layer). Same authoring experience, different destination. Know both exist and how to pick: BI reporting pipeline → Power BI dataflow; loading Dataverse for apps → Power Platform dataflow.

Q87: "How do you share and govern Power BI content?"#

Know this
Content lives in workspaces; you package curated content as a Power BI app for consumers. Sharing needs licensing: Pro per-user, or Premium / Fabric capacity (F/P SKUs) for broad or heavy workloads. Governance levers: workspace roles (Admin/Member/Contributor/Viewer), sensitivity labels, endorsement (Promoted/Certified datasets), deployment pipelines for Dev/Test/Prod (the BI equivalent of the ALM you already do), and tenant settings in the Fabric/Power BI admin portal.

Q88: "Power BI vs Excel — when Power BI?"#

Know this
Excel is unbeatable for ad-hoc, free-form, single-user analysis. Reach for Power BI when you need a refreshable, modelled, shareable report over larger or multi-table data with governed access, interactive cross-filtering, and a single version of the truth. In short: one-off exploration → Excel; a repeatable governed report many people rely on → Power BI.
Careful
Don't overclaim Power BI depth. If pushed past your level (advanced DAX like CALCULATE context transitions, complex time-intelligence, Fabric/Direct Lake), say so cleanly: "That's beyond where I am today — I'm building it through PL-300. What I'm solid on is the modelling and Power Query foundation." Honesty here reads better than a shaky CALCULATE answer.
